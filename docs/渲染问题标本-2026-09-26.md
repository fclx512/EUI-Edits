## 补充二：隔离实例实测（2026-09-26，Obsidian 1.13.7 **Live Preview**）

> 与上一节同一套隔离实例/探针/采集脚本，改成 `livePreview=true`（`参考/obsidian-style/cdp_lp.py`）。
> 产物：`参考/obsidian-style/probe-lp-measure.json`（112 条 `cm-line` 全量几何）、
> `参考/obsidian-style/标本/probe_lp_obs_{light,dark}_full.png`。R1 以**本节**为准，
> 上一节的阅读视图数值（标题前距 40px、块间 16px）不适用于 LP。

**核心结论：LP 的间距在行盒内部，行与行首尾相接**

- 112 行里 `rect.top[i] - rect.bottom[i-1]` 全为 `0`（±0.01 舍入）；唯一的例外是表格部件
  占据的 121.6px（见下）。块间距不是行间空白，而是行盒自己的 `padding-top`。
- 因此**段与段的分离由空源码行自己承担**：实测「空行 → 段落」的段落行 `padding-top: 0px`，
  整篇里除标题行外没有任何一行有非零 `padding-top`。

**逐项实测（CSS px，dpr 1）**

| 项目 | 实测值 |
|---|---|
| 正文 / 空源码行 | 行盒 **24px**（`--line-height-normal 1.5 × 16`），44 条空行无一例外 |
| 标题行 `padding-top` | **16px**；例外：`标题 + 恰好一条空行 + 标题` → **0**（`app.css` 11779） |
| 标题 `line-height` | h1 **1.2**、h2 **1.2**、h3 **1.3**（`--h?-line-height`） |
| 代码行（围栏行含） | **21px** = 14 × 1.5，`padding: 0`（阅读视图 `pre` 的 12px 不适用） |
| 列表项 | **26.4px** = 24 + 1.2 + 1.2（列表行自带 `padding: 1.2px 0`） |
| 表格 | 表体是 `.cm-embed-block.cm-table-widget`（**不是** `cm-line`）：`padding: 16px 16px`、`margin-left/right: -16px`、部件高 **121.6** = 16 + 3×29.6 + 16；行盒 29.6、表内 line-height 1.3 |
| 分隔线 | 行盒 **24px**、`padding: 0`（上下各一条空行给分离，合计 48px） |
| 图片 | 行盒 351px（图片本身），前后各一条空行 |
| 引用 / 嵌套引用行 | 行盒 24px、`padding-top: 0`；引用内 `### 引用内标题` 在 LP 里**不是**标题行（`cls` 仍是 `quote quote-2`） |
| 属性面板（frontmatter） | 高 148.3px，其后是空行 → 首个标题行 |

**新发现：LP 标题行盒被 CodeMirror 撑高约 4px（刻意不复刻）**

同一个 h1，阅读视图行盒 31.06px，LP 行盒 **35.06px**（h2 31.26、h3 29.81；分别多
3.99 / 3.20 / 2.40px）。DOM 消融实验（隔离实例，`build/heading_dom.json`）定位到
CodeMirror 的游标锚点：每条标题行里都有两个 1em 高、`vertical-align: text-top` 的
`<img class="cm-widgetBuffer">` 和一个零宽 `<span contenteditable="false">`。标题字体的
ascent+descent 约 1.45em > `line-height` 1.2em，负半行距把行盒顶到约 1.35em；正文行
（1.5 > 1.45）里这一项正好抵消，所以空行/正文仍是干净的 24px。

结论：这是**渲染器实现痕迹**（数值随本机 CJK 字体度量变化），不是 Obsidian 的设计意图 ——
阅读视图用同一份 CSS 却精确给出 1.2em/1.3em。R1 采用 CSS 声明的比例，接受每个标题行
比 LP 矮 2.4~4px 的累计差，理由与后续处理写在 `docs/块模型契约-2026-09-26.md` §4。

**限制**

- 本轮同样只完成 Obsidian 侧；NeoEditor 侧对照截图仍未采集，R1 的观感验收待双侧配对。
- 列表项 26.4px、表格行 29.6px 是**行盒内部 padding**，R1（块间距）不涉及，已记入
  契约 §6 的待办。

**3. 这一轮修掉的验收脚本问题**（脚本本身，不是产品）

- `verify_live_preview.py` 是旧一代脚本：不钉设置、不校验前台、用已被淘汰的窗口 DC 采集。
  表现是**三次都产出假数据**——第一次截到用户的浏览器整页（前台被浏览器占着，
  `SetForegroundWindow` 从后台进程调用会被系统静默忽略，而窗口 DC 在被遮挡时 BitBlt 会
  拿到屏幕内容）；钉了设置后又因为窗口 DC 读到**冻结帧**，光标/标记全不更新（装饰日志
  显示光标序列 0→4→16→34→27→44 完全正确，像素却是旧的）。已对齐兄弟脚本的写法：
  复用 `verify_task_toggle` 的 `assert_unlocked` / `ensure_foreground` / `capture_client`
  （**屏幕法**），并钉上 `mode/line_numbers/readable_width/theme/字号/缩放`。
- `verify_live_preview.py` 的判据⑥原写"比编辑区背景更暗的像素"且锚定 `(19,22,25)`：
  主题对齐 Obsidian 后底色块是 `#232323`，深色下比页面底色**更亮**，判据恒为 0。
  改成"带内最大同色计数"（不锚色值、不假定亮度方向），阈值 200 不变即可
  （实测行内代码行 355、纯文字行 134，余量充分）。
- `verify_image_block.py` 的判据②左缘上限 60px 是按"无限制行宽"标定的：`readable_width`
  打开时内容列居中，文本原点右移到 115 物理像素 → 恒 FAIL。钉 `readable_width=0` 后
  回到 23px ✓（也顺带与 Obsidian 探针条件一致）。

  代码块标点形态，需按渲染器可变字体那条已知坑换 Consolas 再看。

## 补充四：代码块字符挤在一起 / 选择错位——根因与修复（2026-09-26）

**症状（用户实机反馈）**：代码块内部字符间距不对，符号挤在一起、有重叠感；拖动选择时
选框与字形错开，看上去"盖到旁边的字上"。肉眼可复现的两个硬证据：`function hello(name) {`
画成 `functionhello(name) {`（**关键字后的空格消失**）、
`` return msg ?? `n=${count}`;`` 的**结束反引号消失**。

**定位过程**（三步，每步都留了可复跑的探针）

1. **先量像素，怀疑字形本身**：把 `focus.md` 采成 PNG 后按列统计墨迹起点，发现同一行里
   相邻字符的墨迹间距是均匀的 11 物理像素；而布局层给的每字符宽度是 8.0 逻辑像素
   （= 10 物理像素）——两边差 10%。也就是说**画出来的字比排版时预留的格子宽**。
2. **再给渲染循环加临时日志**（`NEO_INPUT_DUMP`，看完即删）：布局完全正确 ——
   `function ` 段 x=16 宽=72，`hello` 段 x=88，各段宽都按 8.0/字符算。但既然每段内部
   按 11 物理像素排字，**每段都会溢出自己的矩形**，下一个段照布局给的 x 落笔，正好压掉
   前一段的最后一个字符 —— 空格、反引号就是这么没的，选区（按同一份 x 累加）也就跟字形错开。
3. **再打印渲染器真正加载的字号**：`LOADFONT fam=[...CascadiaCode.ttf] size=17.500`。
   根因清楚了：`runtime_render.h` 交给 TextPrimitive 的字号是**设备像素**
   （逻辑 14 × DPI 1.25 = 17.5），`FT_Set_Char_Size` 取 `round(17.5) = 18` ppem；
   而排版层（`input_model`）拿的是**逻辑 14**，自己的 ppem 是 14。带 hinting 时
   FreeType 把左右边距 snap 到整数像素，advance 不是字号的线性函数：
   Cascadia 在 ppem 18 得 11 设备像素、在 ppem 14 得 8 逻辑像素 —— 6~10% 的差全从这来。

**另外半个原因**（改之前就在的那条）：`loadGlyphAdvance` 一直用 `linearHoriAdvance`
（**未 hint** 的线性推进量）去配**已 hint 的字形**。14px 下 Consolas 线性 7.70 而字形
墨迹宽 8px，于是每个字符固定压 0.3px —— 这就是最初"符号糊成一片"的来源。逐字符对照图
（现管线 / 只改推进量 / 两种字体并排）见 `参考/obsidian-style/标本` 之外的临时产物
`build/advance_compare.png`（四点对照：Consolas 现管线/修后、Cascadia 现管线/修后）。

**修法（两处，缺一不可）**

- `core/render/text.cpp` 的 `loadGlyphAdvance`：推进量改用 **hint 后的 `advance.x`**
  —— 它描述的才是马上要被栅格化的那枚字形的格宽。
- 新增 `core::TextPrimitive::setLayoutPixelScale(scale)`：排版层在逻辑像素空间工作，
  必须知道设备缩放才能取到与渲染同一个 ppem。`measureTextMetrics` / `measureTextSize`
  用「逻辑字号 × scale」去量、再把结果除回逻辑单位；`include/eui/detail/dsl_app_impl.h`
  在每帧 `update()`/`render()` 里用框架既有的 `effectiveScale = dpiScale × uiScale`
  设置它。默认 1.0，未设置时行为与老实现完全一致（单测不受影响）。

**结果**：代码块字符步距两边都变成 8.8 逻辑像素（11 设备像素），空格与结束反引号回来，
caret / 选区矩形与字形对齐。`focus_neo.png` 里 `function hello(name) {` 与
`` `n=${count}`; `` 均完整。

**同时纠正一条旧结论**：上一轮把"Cascadia（可变字体）标点缩小下沉"归因到本管线的 VF
处理，本轮用同样 flags 在 12/13/14/15/16…24px 逐档复测 `; : { } ( ) = -` 的墨迹尺寸，
**没有复现**（14px 下 `;` 4×12、`M` 8×11，与 Pillow 无 hint 的结果同量级）。当时的
"挤作一团"就是上面这条推进量不一致，与 VF 无关。

**遗留（需要圈认的取舍）**：带 hinting 时每字符步距被量化成整数设备像素（11），
比 Obsidian/浏览器的小数推进量（0.5859em × 17.5 = 10.25）宽约 7%，代码块整体略宽松。
换来的是字干落在整像素上（本管线一贯的清晰度取舍）。若要像素级对齐 Obsidian 的宽度，
就得改成无 hint 栅格化 + 线性推进量（字会变糊），二选一。
