# EUI-Edits 后续优化方向（2026-10-05）

本轮先确定问题、原因线索和后续调查顺序，等待下一轮实施。优先依据低配电脑上的真实感受，沿用 NeoEditor 的轻量原生编辑器定位。本文没有运行新基准、复现卡顿或修改实现；源码路径能够说明可能的开销来源，不能代替现场耗时测量。

## 优先级与目标

| 顺序 | 用户反馈 | 优先目标 | 后续处理入口 |
| --- | --- | --- | --- |
| 1 | 鼠标拖拽并滚动划选时，选得越多 CPU 越高；约八万字符 JSON 已明显卡顿 | 拖选持续响应，停止拖动后及时稳定；开销主要随可见内容和本次变化，而不是累计选区长度放大 | 先建立拖选专项基线，定位输入、命中、滚动、布局和呈现开销 |
| 2 | 打开文件众多的复杂项目，数秒后才呼出窗口，低配机器更明显 | 窗口与当前文档先可用，目录关系在后台补齐；重复打开同一根尽量复用已有结果 | 优先核对启动及显式打开中的同步扫描，再研究轻量目录模型 |
| 3 | 大文档内存与性能仍需改善，自动换行时尤甚 | 降低首开、换行、编辑、滚动的耗时及峰值/常驻占用，同时保留排版与编辑正确性 | 先分场景计账和定目标，随后逐项调查长行换行、布局收尾及缓存生命周期 |

前两项同属近期体验问题，调查按以上顺序开展；目录的同步扫描入口已能从源码确认，可作为单独的小批次处理。大文档专项持续跟进，但不与目录模型、文本存储、渲染后端一起大改。

## 1. 鼠标拖拽滚动划选

### 为什么优先

这是持续交互中的卡顿，会直接影响定位、复制和简单文本编辑。约八万字符已触发明显问题，不能只以极大文件边界解释。用户在任务管理器中观察到近似指数级上涨，本文保留为待验证的增长感受；尚不能确认指数复杂度，也不能将字符数直接当成 UTF-8 字节数。

要把“正在拖选”与“按下复制后”分开测量。复制选区文本确实需要分配与写剪贴板，但不能用这项一次性成本解释尚未复制时的持续 CPU 负载。

### 已核对的事实与原因线索

| 状态 | 源码事实 / 判断 | 对后续调查的意义 |
| --- | --- | --- |
| 已确认 | `components/input.h:539` 的拖动回调更新光标、选区并同步滚动 | 拖动、滚动和下一帧重建必须分别计时，识别重复帧或无变化事件 |
| 已确认 | `components/input_model.h:1140` 的 `buildSelectionRects` 取选区与可见行的交集 | 当前不是为全部离屏选中文本生成背景矩形；优先查其他链路 |
| 已确认 | `apps/neo_editor/ui/editor_view.h:195` 将正文传入 `InputBuilder::value(std::string)`，`components/input.h:53` 按值保存；`:272` 比较输入状态与正文 | 界面构建中存在全文传递/比较成本。是否主导卡顿、是否随帧数放大仍需测量 |
| 已确认 | `components/input_model.h:897` 复制光标行 metrics，多个输入回调按值捕获 layout | 超长未换行行可能带来字符度量数组与回调副本成本；格式化/压缩 JSON 要分开对照 |
| 已确认 | 源码高亮在 `source_decorations.h:43` 按 revision、长度、语言和配色命中缓存；状态栏在 `status_bar.h:79` 按文档 revision 缓存统计 | 不应预设每次选区变化都会全文重新高亮或统计字符；通过计数确认实际命中率 |
| 待验证 | 滚动跨新可见行触发度量补建；长行命中、文字节点创建、渲染缓存失效或鼠标事件频率可能放大成本 | 累计选区长度与滚动距离、冷行数、单行长度可能相关，必须控制变量 |

单纯看总 CPU 百分比不能区分这些情况。同一文件、同一视口与选区终点，改变选区锚点，可隔离“选区长度”的影响；保持相同滚动轨迹，取消选区，可隔离“滚动”的影响。

### 优化方向与验收重点

先记录每帧耗时、UI 线程 CPU 时间、输入排队时间、布局全量/局部次数、度量行数、选区矩形数和明显停顿，再选择对应改动：

- 若全文传递是热点，建立可信文档身份与 revision 传递，避免未变正文随交互帧反复复制/比较；保留外部赋值、换页与 IME 合成的安全失效路径。
- 若回调/metrics 副本是热点，缩小事件快照或共享只读数据，并明确布局代次和生命周期，避免引用失效或读取旧行。
- 若事件与帧重复是热点，合并同一帧的鼠标移动更新，无实际变化时不重做工作；不能通过丢失最终选区或削弱滚动响应来降低负载。
- 若可见行补建或长行命中是热点，检查缓存复用与查询算法，保持选区绘制按视口限制，不恢复全选区度量。

最小样本覆盖约 8 万字符的格式化 JSON、压缩为长行的 JSON、同规模纯文本；开/关自动换行，分别进行固定视口拖选、跨屏滚动拖选、纯滚动、静止大选区和随后复制。扩展至不同选区长度与文档大小，记录字符数、字节数、物理行数、视觉行数。

验收以低配电脑连续拖选顺畅、选区端点准确、停手后无持续忙算为主，比较相同轨迹下的每帧延迟分位数与 CPU 时间。复制结果、反向选择、中文/emoji 边界、撤销与 IME 不能退化。具体延迟预算在基线取得后确定。

## 2. 复杂目录打开与首个窗口响应

### 为什么会等待

目录开销本身随文件数、目录深度、磁盘与权限状态变化；不合理之处是让整棵目录处理成为窗口可用的前提。当前源码存在明确的同步路径：

```text
app.cpp::appConfigStorage -> restoreSession -> refreshVault
选择文档库 / 部分打开、新建、重命名等显式动作 -> refreshVault
refreshVault -> vaultcache::requestScanSync -> runScan -> vault::scan
```

定位：`app.cpp:381-384`、`:174-183`，`app_actions.cpp:732-746`，`vault_cache.cpp:275-298`。`vault.cpp` 递归枚举普通子目录、查询元数据、排序并构造完整树；因此同步调用足以形成随目录规模增长的阻塞。它能够解释用户反馈的一部分机制，但本轮没有测得其占几秒等待的比例。启动文件读取/解码、恢复、主题/字体及首次正文布局也应单独计时。

后台扫描并非缺失：`vault_cache.cpp:137` 已有调度、代次与共享快照；`app_actions.cpp:671` 采纳快照，`:724` 请求后台刷新。问题首先是哪些入口仍强制同步完成，而不是继续添加另一套重复扫描器。

### 分层优化方向

| 层次 | 方向 | 必须保留的语义 |
| --- | --- | --- |
| 首次响应 | 启动和打开先呈现窗口/当前文档，目录显示加载状态，后台建立关系 | 冷启动无快照也能接收首代结果；旧根内容不能冒充新根 |
| 显式动作 | 重命名、新建、删除成功后先更新相关节点，再异步校验；按需采用轻量刷新 | 文件系统操作成功与失败是权威结果，不用过期索引做覆盖或删除判断 |
| 目录关系 | 评估按目录惰性展开、节点 ID/父子关系、减少重复路径与重复排序 | 隐藏文件、无扩展名文件、权限错误提示与链接目录边界继续保留 |
| 展示 | 复用已有 `virtualList` 可见行绘制，继续核对树展平、过滤和节点构建的前置成本 | 行数与滚动范围正确，当前文件定位、展开状态和排序保持稳定 |
| 更新 | 合并重复请求，对变化子树更新；过期任务不发布，必要时可取消 | 保留现有 request epoch 防旧代回写，补足退出、切根与异常恢复 |
| 重复打开 | 先评估进程内缓存复用；跨启动持久化索引作为后续候选 | 陈旧数据需可识别、可校验；不能漏掉未运行期间的新增/删除/移动 |

仅把扫描移到线程仍可能在结果采纳、树展平、排序或 UI 构建时卡顿；这些阶段也需要计时和工作量边界。首窗可用时间、首批目录可用时间、目录完整时间必须分开报告，后台完成变慢时也应呈现真实加载状态。

现有侧栏已虚拟绘制可见行；扫描树本身仍完整驻留。目录监听目前将事件转换为变更计数，防抖后重扫整根，事件对应的子路径没有用于局部更新。冷页首次扫描还需核对空快照状态下的采纳路径：`tickVaultScan` 对空 `vaultScan` 提前返回，不能仅把同步调用替换为排队而忽略首代结果如何显示；本轮不据此认定已发生故障。

### Everything 思路的可行性边界

可以借鉴“只处理名字与目录关系、复用索引、增量接收变化”的原则。Everything 官方说明其 NTFS 索引使用 USN Journal 更新，并需要服务或管理员权限；普通文件夹索引覆盖更多位置，但比原生 NTFS 索引慢。[官方 FAQ](https://www.voidtools.com/faq/)、[Folder Indexing](https://www.voidtools.com/support/everything/folder_indexing/)。

据此推断，不能把 Everything 的索引速度直接当成普通递归枚举的预期，也不能只替换树容器就期待同等效果。本项目先复用已有后台调度并消除首窗的同步依赖，再比较惰性枚举、局部更新和轻量缓存。卷级索引、USN 读取或调用 Everything 是后续独立可行性议题，届时再核对权限、文件系统、网络盘、日志失效、依赖与维护成本；本轮不选定方案。

目录基线应覆盖文件数、层级和同级数量的增长，以及冷/暖打开、从文件启动/手动选择目录、权限失败、链接目录和连续切根。验收目标是目录尚未完成时窗口也能操作，显式文件动作仍准确，后台不会因重扫反复阻塞 UI；深层搜索的完整性不能以省略目录来换取。

## 3. 大文档占用与自动换行

### 当前剩余成本

现有 viewport caret metrics 只对启用该功能且 UTF-8 正文至少 256 KiB 的文档生效。约八万字符是否跨过门槛取决于编码内容，不能据字符数猜测；表格保留完整字符度量。普通行字符数组可释放，整篇行表、换行段、几何和部分样式数据仍常驻。

`components/input_model.h:2310` 的首次/全量布局测量整篇正文；`:2348` 的布局收尾仍有全文缓存副本及条件性的全行宽度/几何更新。`:3328-3356` 的普通长行换行先取得完整 metrics，再对切出的段度量。源码说明了冷路径与换行成本，尚不能据此计算内存占比或预计加速倍数。

已有不可变分页装饰与局部 replacement，需要保留新旧代次安全；不能把历史“整张装饰表深拷贝”直接当作当前所有路径的事实。表格、复杂样式、宽度改变、编辑增量判据失败仍应列为独立观察项。

### 先确立的目标

- 建立正文、输入状态、缓存正文、当前/上一代解析计划、装饰、布局行、caret 数组、表格、撤销历史和渲染资源的账本，区分峰值与稳定驻留，避免把缓存预算当进程总上限。
- 分开测首次打开、开关自动换行、改变窗口宽度、局部输入/删除、滚动、拖选、切页与保存；选取相同字节数而行数/最长行不同的样本。
- 优先减少重复正文与重复度量，再收敛布局收尾、几何更新和高成本回退；评估长行分段复用及换行结果缓存，命中条件覆盖文档代次、字体、字号、宽度、DPI 与装饰。
- 不活动页释放可重建数据，活动页限制可丢弃缓存；保留正文、撤销、选区、折叠与未保存草稿。释放内存也不能导致频繁重建造成更严重的滚动或切页停顿。

目标是同机同条件下取得可重复的净收益，低配电脑编辑体验不退化。沿用此前不强求 100 MiB 死线的原则；具体容量与延迟目标在新账本和场景基线完成后确定。

当前 [9 MiB 文档闲置实测](内存实测-2026-10-05.md)可作起点，后续补充长行 JSON、自动换行与交互峰值，不能用这组空闲读数代替整个专项验收。

| 批次 | 只在后续执行的工作 | 阶段产出 |

后续每项性能结论需绑定候选 EXE 的 SHA256、样本文档特征、机器/字体/DPI/窗口/设置、相同操作和正常退出。CPU 比较记录采样方法与线程时间，内存区分整体工作集、专用工作集、专用提交量；不通过强制收缩工作集制造收益。至少覆盖中文/emoji、反向选区、换行、保存/撤销/恢复、目录切换与文件操作，实施后再声明通过。

具体执行步骤与回填模板见[性能测试计划](EUI-Edits-性能测试计划与结果-2026-10-05.md)。测试代理只执行测试并回填该文档，完成后由主代理阅读结果，再安排修复。
