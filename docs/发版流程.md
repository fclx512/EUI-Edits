# EUI-Edits 发版流程

本文件是每次创建 EUI-Edits 发行版前的固定入口。它规定候选冻结、验证、文案复核和授权顺序；脚本的参数与底层检查见[发布构建说明](NeoEditor-发布构建说明-2026-10-02.md)，开发过程和交接字段见[开发流程与交接规范](开发流程与交接规范.md)。

发版流程只处理已经确定要交付的候选。正在开发的 dirty 工作树、未完成的性能调查和仅有源码检查结果的功能，不得直接当作发行候选。

## 1. 建立候选快照

开始发版前，在仓库根目录保存以下信息：

```powershell
git status --short --untracked-files=all
git branch --show-current
git rev-parse HEAD
```

逐项确认：

- 本次候选包含哪些提交、dirty 文件和未跟踪文件；每个文件都有明确归属。
- 产品版本和发布类型（正式版、预发布版或内部包）已经确定。
- 新构建、测试和打包证据使用 `out/` 下的全新目录，不覆盖旧证据。
- 未完成改动、未验证功能和计划中的后续工作不进入候选，或者明确写入发布说明的已知限制。

候选范围未冻结前，只做调查和开发验证，不运行正式打包，也不修改 GitHub Release 内容。

## 2. 统一版本与对外文案

产品版本的单一来源是 `cmake/NeoEditorVersion.cmake` 中的 `NEO_EDITOR_VERSION`。内部目录、CMake 目标和脚本继续使用 `neo_editor` 等既有标识；对外产品名、可执行文件名和 GitHub Release 名称使用 **EUI-Edits**。

版本确定后，按下面的顺序核对所有需要同步的位置：

1. `cmake/NeoEditorVersion.cmake` 的默认版本或本轮 CMake 参数。
2. `scripts/package-neoeditor.ps1` 的默认版本（如果默认值随版本更新）。
3. `apps/neo_editor/RELEASE-NOTES.md` 的标题和版本说明。
4. `README.md` 与 `README_EN.md` 的发布页链接、EXE 文件名、版本摘要和已知平台边界。
5. GitHub Release 的标题、标签、资产名称和正文。

版本、文件名、链接或摘要有一处不一致，就回到本阶段修正，不能用发布页人工解释替代仓库文案同步。

## 3. 编写发布说明

发布说明沿用 `apps/neo_editor/RELEASE-NOTES.md` 当前风格：版本标题、简短版本说明、`本次更新`（或对应英文摘要）以及按用户可感知领域分组的条目。每个条目说明实际行为、适用条件和已知边界；性能描述必须有本轮证据支持。

发布说明应当：

- 先写用户能观察到的变化，再写必要的实现背景。
- 把修复、改进、限制和未覆盖平台分开表述。
- 与中英文 README 的一句话摘要保持同一事实范围。
- 保留必要的“更新方法”或迁移提示，并确认它适用于本版本。

发布说明不维护哈希文件表，也不把哈希值复制进 README 或版本说明。最终 EXE 的 SHA256 由维护者在本地核验，并在 GitHub 上传资产后再次确认资产与本地候选一致。

## 4. 运行正确性门禁

使用 PowerShell 7（`pwsh`）和全新的唯一构建目录运行：

```powershell
$EuiBuildCMake = 'D:/ruanjian/Microsoft Visual Studio/Community/Common7/IDE/CommonExtensions/Microsoft/CMake/CMake/bin/cmake.exe'
pwsh -NoProfile -File ./scripts/check-neoeditor.ps1 `
  -BuildDirectory ./out/release-check-<唯一名称>/build `
  -CMake $EuiBuildCMake -Python D:/Python312/python.exe -Parallel 6
git -c core.whitespace=cr-at-eol diff --check
```

门禁必须同时覆盖翻译检查、配置、Release x64 构建、脚本选择的完整 CTest 集合和 `diff --check`。测试数量以本轮 `scripts/check-neoeditor.ps1` 的 `$targets` 及语言案例为准，文档不得沿用旧轮次的固定数量。

任何配置、编译、测试或文案检查失败，都停止发版并保留本轮日志、构建目录和失败原因。旧轮次的通过记录不能替代当前候选的门禁。

## 5. 生成独立正式包

正确性门禁通过后，再使用新的 build/output 目录运行 `scripts/package-neoeditor.ps1`。构建参数必须对应正式包：Windows、MSVC x64、Release、Win32、Direct2D、bundled 依赖、静态框架和运行库，并使用候选版本。

打包脚本负责检查 CMake 缓存、PE 产品/文件版本、x64、系统 DLL 依赖、开发路径、嵌入许可证和空目录中的许可证导出。输出目录必须为空或不存在；开发 EXE、旧包和其他 checkout 的缓存都不能改名后充当正式包。

打包完成后确认：

- EXE 文件名、产品版本和 GitHub Release 资产名一致。
- 许可证可以从单 EXE 导出，且不依赖旁置资源目录。
- 资产复制完成后没有被改写。
- 本地维护记录已经保存候选 EXE 的 SHA256，供上传前后核对使用。

SHA256 是发布资产的核验依据，不是发布说明内容；仓库不维护哈希文件表。

## 6. 独立完成真实窗口和性能验收

正确性门禁和打包通过后，仍须分别处理真实窗口和性能验收。验收记录绑定最终候选 EXE、独立配置目录、窗口和设备条件，并使用以下状态词：

- `PASS`：指定动作已执行且满足通过条件。
- `FAIL`：指定动作已执行但不满足通过条件。
- `OBSERVED`：观察到现象，但证据不足以判定通过或失败。
- `SKIP`：本轮有明确的工具、设备或范围原因未执行。
- `NOT_RUN`：本轮尚未执行。

至少检查与本版本相关的保存、恢复、撤销、文件关联、菜单、输入法、图片/Markdown、窗口生命周期和正常退出。GPU、低配、多屏 DPI、持续拖选等场景只有实际覆盖才能写 `PASS`；单元测试、截图、`EndDraw` 成功和无头模型测试不能代替真实操作。

性能记录测试规模、配置、预热、原始轮次、指标定义、统计口径、源码身份和候选 EXE SHA256。不要把微基准结果写成整体 CPU、内存、输入延迟或硬件 GPU 的结论。

必测项出现 `FAIL`、`NOT_RUN` 或无法绑定候选 EXE 时，停止发版；确实不在本版本范围内的项目必须在本地验收记录和发布说明中写清边界。

## 7. 发布前最后复核

在任何 Git 操作或 GitHub 操作前，逐项复核：

- 产品版本、标签、下载链接、EXE 文件名和输出目录一致。
- `RELEASE-NOTES.md`、中文 README、英文 README 与实际候选行为一致。
- 已知限制、未覆盖平台和更新方法已经写明。
- 正确性门禁、独立打包、真实窗口和性能记录都绑定本轮候选。
- 发布正文不包含哈希文件表；哈希仅用于维护者本地和 GitHub 资产核验。
- `out/` 原始证据和 `local-docs/` 轮次记录路径已经写入交接快照。
- 剩余 `FAIL`、`SKIP`、`NOT_RUN` 已分类，并确认没有阻断项。

建议用 `scripts/write-handoff-summary.ps1` 生成本轮交接快照，至少记录候选范围、构建目录、测试结果、包路径、验收状态、证据位置、剩余缺口和授权状态。

## 8. 授权边界与完成条件

构建、测试、文档检查和本地验收可以在任务范围内执行。提交、推送、打标签、创建或编辑 GitHub Release 属于最后的对外动作，必须获得本轮明确授权；历史版本的授权不自动延续到新版本。

只有在候选已冻结、版本和文案一致、必测项通过、正式包完成、真实窗口与性能缺口已明确、哈希已由维护者核验并且授权状态明确后，发版前流程才算完成。发布动作本身按授权范围执行，完成后把标签、Release 资产和最终状态补回本地交接记录。
