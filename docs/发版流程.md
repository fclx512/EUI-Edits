# EUI-Edits 发版流程

本页维护候选到公开发行的顺序；日常验证和产物管理见[开发与维护规范](开发流程与交接规范.md)，底层命令见[构建参数与脚本](NeoEditor-发布构建说明-2026-10-02.md)。

固定路线：**冻结范围和版本 → 预检 → 完整检查 → 独立包 → 候选 GUI → 审核提交 → 新检出 / 远端验证 → 标签与 draft → 最终资产 GUI → 发布 → 下载复核**。一个主代理负责本轮候选，冻结期间串行构建。

## 1. 冻结范围与文案

记录分支、HEAD、dirty/untracked 归属及本次候选范围，确定版本与发布类型。按开发规范完成本次源码的文档同步记录后冻结，预检会核对其内容摘要和结论。产品版本源是 `cmake/NeoEditorVersion.cmake`；对外使用 EUI-Edits，内部目录和目标保留 `neo_editor`，新标签使用 `neoeditor-v<版本>`。

先中文后英文核对以下文案：

- `apps/neo_editor/RELEASE-NOTES.md`：用户可感知的变化、适用条件和更新方法。
- `README.md`、`README_EN.md`、`apps/neo_editor/README.md`：版本摘要、操作、平台及下载入口。
- workflow 输入、标签、Release 标题、EXE 名称与候选版本。

先写实际行为，性能结论引用本轮条件；尚未实测的环节简述范围。SHA256 保存在本地验收记录及资产校验文件，发布正文保持简洁。

## 2. 统一准备入口

在 PowerShell 7 中先运行预检：

```powershell
$EuiReleaseVersion = '<已确认且同步到版本源的版本>'
pwsh -NoProfile -File ./scripts/prepare-neoeditor-release.ps1 `
  -Version $EuiReleaseVersion -Python D:/Python312/python.exe `
  -Parallel 2 -PreflightOnly
```

预检检查工具、生成器、版本、目录、翻译、文档、`diff --check HEAD` 与源码身份。通过后去掉 `-PreflightOnly` 执行正式检查和独立包；默认并发为 2，输出为 `out/stable-candidate/`。已有非空候选先交接，保留原资产。

| 结果 | 下一步 |
| --- | --- |
| PREFLIGHT_PASS | 冻结后运行完整准备 |
| FAIL | 查看 `result.json` 与失败阶段日志，修复后新建轮次 |
| READY_FOR_GUI | 对生成的最终 EXE 做实窗验收 |

入口在唯一 `out/release-prepare-*/` 中保存参数、工具、退出码、日志和 tracked/untracked 文件身份，阶段间检测 HEAD、状态与内容变化。正式输入应纳入源码清单。锁覆盖统一入口，冻结期间也须暂停其它编辑和直接构建。

成功后保存 EXE、哈希、配置和 CTest 日志，再清理本轮两棵构建树。`-KeepBuildDirectories` 用于继续排查；失败时保留构建树和 MSBuild 诊断，排查结束后按开发规范清理。部分生成的候选连同失败记录保留，重跑另建目录。

## 3. 正确性与独立包

统一入口先运行 `scripts/check-neoeditor.ps1`，成功后运行 `scripts/package-neoeditor.ps1`。完整检查包含文档及其回归、翻译、Release x64 构建、当前脚本选定的 CTest 集合；测试数从实际枚举取得。

包使用 MSVC x64 Release、Win32 / Direct2D、bundled 依赖、静态框架和 CRT、内嵌资源。打包检查缓存、PE 版本/x64、系统 DLL 依赖、开发路径和许可证导出，保存最终 EXE SHA256。正式包从新构建生成；`-SkipBuild` 仅用于排查。

失败按工具、配置、编译、断言、包检查或 GUI 定位。`MSB4166` 同时保留 MSBuild 诊断，再据实际原因处理。正式 CTest 含 HWND 测试，需要桌面条件；需要完全后台运行时只做预检或明确的后台子集，完整门禁记 `NOT_RUN`。

## 4. 最终包验收

验收绑定最终 EXE SHA256、独立配置、所属窗口和设备条件。按本版本改动检查保存/恢复、撤销、菜单、文件关联、图片/Markdown、IME 与正常退出；性能另外记录规模、预热、原始轮次和统计口径。具体状态使用开发规范中的 `PASS`、`FAIL`、`OBSERVED`、`SKIP`、`NOT_RUN`。

必测项通过后进入发布复核。未覆盖的 Windows 10、GPU、低配、多屏 DPI、持续拖选等在本地记录中逐项注明，涉及产品承诺的范围同步到文案。外置测试台与历史报告保留其原有覆盖范围。

## 5. 提交、标签与 draft

提交、推送、标签和 GitHub Release 操作按用户本轮授权执行。对外标签指向已审核提交；获提交与推送授权后，记录唯一 SHA，等待该 SHA 的新检出 / Windows checks 通过，再做标签。新检出使用自己的脚本和构建目录，记录 `core.autocrlf` 与文本夹具的实际换行。

已有标签原地保留。workflow 环境失败可重跑原标签原 SHA；源码修复形成新候选与新版本。查询 draft 时枚举 Release 并按 `tag_name` 匹配，确认已有状态后操作。

标签 workflow 创建 draft。从 draft 下载最终 EXE 和 `.sha256`，核对版本与哈希，并在该资产上完成必测 GUI 和正常退出；哈希变化时重新验收。采用直接上传本地已验收包时，按明确授权协调自动 draft 路径，保持资产唯一。

## 6. 发布与收尾

确认版本、文案、最终资产、必测结果和发布授权一致后公开 Release。随后重新下载，核对 EXE 哈希、版本和资产清单。

更新本地交接：候选范围、审核提交、标签、Release 地址、最终资产与哈希、检查及实窗结果、剩余事项。候选归档按开发规范第 4 节执行。
