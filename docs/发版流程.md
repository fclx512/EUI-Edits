# EUI-Edits 发版流程

本文件是每次创建 EUI-Edits 发行版前的固定入口。它规定候选冻结、验证、文案复核和授权顺序；脚本的参数与底层检查见[发布构建说明](NeoEditor-发布构建说明-2026-10-02.md)，开发过程和交接字段见[开发流程与交接规范](开发流程与交接规范.md)。

发版流程只处理已经确定要交付的候选。正在开发的 dirty 工作树、未完成的性能调查和仅有源码检查结果的功能，不得直接当作发行候选。

## 固定执行路线

一次更新只由一个主代理负责候选冻结、构建和对外动作；Luna 可只读盘点、核对证据或处理指定文档。不同时运行多个代理的全量构建，不在门禁运行中继续编辑候选。

固定顺序为：**冻结范围/版本 → 预检 → 完整正确性门禁 → 独立包 → 最终包 GUI → 审核提交 → 新检出/远端验证 → 授权标签与 draft → draft 最终资产验收 → 发布 → 下载复核**。每阶段只接受绑定当前源码和资产的结果。

统一入口是 `scripts/prepare-neoeditor-release.ps1`。先运行预检：

```powershell
# 设为本轮已确认且已同步到版本源的版本；不要复用已发布版本。
$EuiReleaseVersion = '<已确认版本>'
pwsh -NoProfile -File ./scripts/prepare-neoeditor-release.ps1 `
  -Version $EuiReleaseVersion -Python D:/Python312/python.exe `
  -Parallel 2 -PreflightOnly
```

预检只检查实际 Visual Studio/CMake 生成器支持、Python 3、CTest、dumpbin、版本、路径、空候选目录、翻译、`diff --check HEAD` 和源码前后身份；不编译、不运行 CTest、不生成候选、不打开应用。已有 `stable-candidate` 非空时立即停止，先交接该候选，不自动覆盖。

冻结范围且桌面测试条件就绪后，同样命令去掉 `-PreflightOnly`。默认并发 2，先跑完整门禁，成功后才打包到 `out/stable-candidate/`，没有跳过门禁的开关。正式 CTest 含原生 HWND 合同；它不是纯后台模型集合，更不是人工编辑验收。需要桌面完全无窗口活动时，只做预检或本机测试台的明确后台子集，完整门禁记为 `NOT_RUN`。

| 入口结果 | 含义 | 下一步 |
|---|---|---|
| `PREFLIGHT_PASS` | 工具、目录、翻译和身份通过 | 冻结后运行完整准备 |
| `FAIL` | 阶段失败、源码漂移或并发冲突 | 读取 `result.json` 和对应日志，修复后新建轮次 |
| `READY_FOR_GUI` | 当前源码的正式门禁和独立包通过 | 对生成 EXE 完成必测 GUI；不是允许发布 |

入口自动创建唯一 `out/release-prepare-*/`，保存命令参数、逐阶段退出码、日志、工具路径、tracked/untracked 文件 SHA256 和源码前后清单。HEAD、Git 状态或文件内容在阶段间变化就停止；失败也尽力保留最终身份快照。忽略的个人配置、`local-docs/` 和产物不进入源码清单，正式输入不得藏在忽略目录中。锁只约束该入口，不能阻止其它编辑器或直接 CMake 命令，所以仍须禁止并行修改/构建。

成功后保留最终 EXE、哈希、CMake 配置和 CTest 日志，再删除本入口创建的两个构建树。失败保留构建树和 MSBuild 诊断，排查结束后按开发规范清理。重跑使用新证据目录；失败留下部分候选时先核对归属并保留，不能覆写或视为通过。

本机外置 eui-testbench 仍按其计划运行；`all-background`、普通退出码 0 和 CPU `OBSERVED` 不代替正式名单通过。该入口统一本地/CI 的正式准备，不替代性能或 GUI，也不要求小改动每次跑完整门禁。

## 1. 建立候选快照

开始发版前，在仓库根目录保存以下信息：

```powershell
git status --short --untracked-files=all
git branch --show-current
git rev-parse HEAD
```

逐项确认：

- 本次候选包含哪些提交、dirty 文件和未跟踪文件；每个文件都有明确归属。
- 产品版本和发布类型（正式版、预发布版或内部包）已经确定。
- 新构建、测试和打包证据使用 `out/` 下的全新目录，不覆盖旧证据。
- 未完成改动、未验证功能和计划中的后续工作不进入候选，或者明确写入发布说明的已知限制。

候选范围未冻结前，只做调查和开发验证，不运行正式打包，也不修改 GitHub Release 内容。

## 2. 统一版本与对外文案

产品版本的单一来源是 `cmake/NeoEditorVersion.cmake` 中的 `NEO_EDITOR_VERSION`。内部目录、CMake 目标和脚本继续使用 `neo_editor` 等既有标识；对外产品名、可执行文件名和 GitHub Release 名称使用 **EUI-Edits**。

版本确定后，按下面的顺序核对所有需要同步的位置：

1. `cmake/NeoEditorVersion.cmake` 的默认版本或本轮 CMake 参数。
2. 打包脚本从版本源读取默认值；统一入口要求显式版本与源码一致，并核对 workflow 手动输入值。
3. `apps/neo_editor/RELEASE-NOTES.md` 的标题和版本说明。
4. `README.md` 与 `README_EN.md` 的发布页链接、EXE 文件名、版本摘要和已知平台边界。
5. GitHub Release 的标题、标签、资产名称和正文。

版本、文件名、链接或摘要有一处不一致，就回到本阶段修正，不能用发布页人工解释替代仓库文案同步。

## 3. 编写发布说明

发布说明沿用 `apps/neo_editor/RELEASE-NOTES.md` 当前风格：版本标题、简短版本说明、`本次更新`（或对应英文摘要）以及按用户可感知领域分组的条目。每个条目说明实际行为、适用条件和已知边界；性能描述必须有本轮证据支持。

发布说明应当：

- 先写用户能观察到的变化，再写必要的实现背景。
- 把修复、改进、限制和未覆盖平台分开表述。
- 与中英文 README 的一句话摘要保持同一事实范围。
- 保留必要的“更新方法”或迁移提示，并确认它适用于本版本。

发布说明不维护哈希文件表，也不把哈希值复制进 README 或版本说明。最终 EXE 的 SHA256 由维护者在本地核验，并在 GitHub 上传资产后再次确认资产与本地候选一致。

## 4. 运行正确性门禁

统一入口自动执行此阶段；单独排查时使用 PowerShell 7（`pwsh`）和全新构建目录：

```powershell
$EuiBuildCMake = 'D:/ruanjian/Microsoft Visual Studio/Community/Common7/IDE/CommonExtensions/Microsoft/CMake/CMake/bin/cmake.exe'
pwsh -NoProfile -File ./scripts/check-neoeditor.ps1 `
  -BuildDirectory ./out/release-check-<唯一名称>/build `
  -CMake $EuiBuildCMake -Python D:/Python312/python.exe -Parallel 2
git -c core.whitespace=cr-at-eol diff --check
```

门禁必须同时覆盖翻译检查、配置、Release x64 构建、脚本选择的完整 CTest 集合和 `diff --check`。测试数量以本轮 `scripts/check-neoeditor.ps1` 的 `$targets` 及语言案例为准，文档不得沿用旧轮次的固定数量。

任何配置、编译、测试或文案检查失败，都停止发版并保留本轮日志、构建目录和失败原因。旧轮次的通过记录不能替代当前候选的门禁。

失败先分类为 shell/工具预检、CMake 配置、MSVC 编译、CTest 断言、包检查或 GUI，不统称为“构建失败”。读首条错误和退出码再修改，不反复换目录/参数/推标签碰运气。`MSB4166` 要保留 MSBuild 诊断，不能仅凭错误码断言内存不足；并发从 2 开始，只有有证据的环境原因才调整。

## 5. 生成独立正式包

正确性门禁通过后，再使用新的 build/output 目录运行 `scripts/package-neoeditor.ps1`。构建参数必须对应正式包：Windows、MSVC x64、Release、Win32、Direct2D、bundled 依赖、静态框架和运行库，并使用候选版本。

打包脚本负责检查 CMake 缓存、PE 产品/文件版本、x64、系统 DLL 依赖、开发路径、嵌入许可证和空目录中的许可证导出。输出目录必须为空或不存在；开发 EXE、旧包和其他 checkout 的缓存都不能改名后充当正式包。

打包完成后确认：

- EXE 文件名、产品版本和 GitHub Release 资产名一致。
- 许可证可以从单 EXE 导出，且不依赖旁置资源目录。
- 资产复制完成后没有被改写。
- 本地维护记录已经保存候选 EXE 的 SHA256，供上传前后核对使用。

SHA256 是发布资产的核验依据，不是发布说明内容；仓库不维护哈希文件表。

正式发行不使用 `-SkipBuild`。它只用于排查同仓库既有包构建的校验；路径/缓存匹配不证明与当前源码相同。

## 6. 独立完成真实窗口和性能验收

正确性门禁和打包通过后，仍须分别处理真实窗口和性能验收。验收记录绑定最终候选 EXE、独立配置目录、窗口和设备条件，并使用以下状态词：

- `PASS`：指定动作已执行且满足通过条件。
- `FAIL`：指定动作已执行但不满足通过条件。
- `OBSERVED`：观察到现象，但证据不足以判定通过或失败。
- `SKIP`：本轮有明确的工具、设备或范围原因未执行。
- `NOT_RUN`：本轮尚未执行。

至少检查与本版本相关的保存、恢复、撤销、文件关联、菜单、输入法、图片/Markdown、窗口生命周期和正常退出。GPU、低配、多屏 DPI、持续拖选等场景只有实际覆盖才能写 `PASS`；单元测试、截图、`EndDraw` 成功和无头模型测试不能代替真实操作。

性能记录测试规模、配置、预热、原始轮次、指标定义、统计口径、源码身份和候选 EXE SHA256。不要把微基准结果写成整体 CPU、内存、输入延迟或硬件 GPU 的结论。

必测项出现 `FAIL`、`NOT_RUN` 或无法绑定候选 EXE 时，停止发版；确实不在本版本范围内的项目必须在本地验收记录和发布说明中写清边界。

## 7. 发布前最后复核

在任何 Git 操作或 GitHub 操作前，逐项复核：

- 产品版本、标签、下载链接、EXE 文件名和输出目录一致。
- `RELEASE-NOTES.md`、中文 README、英文 README 与实际候选行为一致。
- 已知限制、未覆盖平台和更新方法已经写明。
- 正确性门禁、独立打包、真实窗口和性能记录都绑定本轮候选。
- 发布正文不包含哈希文件表；哈希仅用于维护者本地和 GitHub 资产核验。
- `out/` 原始证据和 `local-docs/` 轮次记录路径已经写入交接快照。
- 剩余 `FAIL`、`SKIP`、`NOT_RUN` 已分类，并确认没有阻断项。

建议用 `scripts/write-handoff-summary.ps1` 生成本轮交接快照，至少记录候选范围、构建目录、测试结果、包路径、验收状态、证据位置、剩余缺口和授权状态。

### 提交后的检出与远端验证

本地 dirty 候选可用于准备/验收，对外标签必须指向已审核提交。获提交/推送授权后记录唯一 SHA；对该 SHA 做全新 Windows 检出并运行同一入口，或等该 SHA 的 Windows checks 成功并下载候选。提交前工作副本通过不代表提交后新检出通过。

全新检出不复用主工作树、旧 CMake cache 或开发 EXE。记录 `core.autocrlf` 和 `git ls-files --eol tests/assets/mindmap/manual-preview.md`，核对实际 LF/CRLF。应用文本夹具通过应用加载路径规范化；考验原始字节的测试显式覆盖换行/编码。临时 clone 可放本轮拥有的仓内证据目录，使用 clone 自己的脚本和构建目录。

推源提交后先等该 SHA 的 Windows checks 成功，确认门禁和独立包均通过，再做标签。新标签沿用 `neoeditor-v<版本>` 内部约定，历史 `v*` 不改写；版本、下载链接和实际选定标签必须一致。已有标签不删除/强推/移动；失败 workflow 重跑原标签原 SHA，源码修复使用新候选与新版本，不悄悄换已发布资产。

标签 workflow 重建后创建 **draft**，不会自动公开。本地、main CI、标签 CI 的 EXE 可能不同，即使源码 SHA 相同也不假设二进制哈希相同。从 draft 下载最终 EXE 与 `.sha256`，绑定它做必测 GUI/正常退出并保存下载校验。哈希不同就重做验收，旧 GUI 通过不能转移。若直接上传本地已验收包，须明确授权并协调自动 draft 路径，保证逐字节一致，不让两种路径同时争夺资产。

查 draft 枚举 Release 并按 `tag_name` 匹配；单次标签查询失败不表示 draft 不存在。查询失败、已有 draft 或已公开 Release 都停止自动创建/替换，先看已有状态。只有最终 draft 资产、验收结果和发布授权一致才公开；公开后再下载验证 EXE 哈希、版本和资产清单并写回交接。远端绿灯不代表已验收或已发布。

## 8. 授权边界与完成条件

构建、测试、文档检查和本地验收可以在任务范围内执行。提交、推送、打标签、创建或编辑 GitHub Release 属于最后的对外动作，必须获得本轮明确授权；历史版本的授权不自动延续到新版本。

只有在候选已冻结、版本和文案一致、必测项通过、正式包完成、真实窗口与性能缺口已明确、哈希已由维护者核验并且授权状态明确后，发版前流程才算完成。发布动作本身按授权范围执行，完成后把标签、Release 资产和最终状态补回本地交接记录。
