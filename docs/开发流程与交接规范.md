# EUI-Edits 开发与维护规范

本文统一规定开发、验证、文档维护和交接。技术细节按[文档导航](目录说明.md)阅读，候选到发布的顺序见[发版流程](发版流程.md)。

## 1. 接手与任务范围

在仓库根目录执行：

```powershell
git status --short --untracked-files=all
git branch --show-current
git rev-parse HEAD
```

先读 `AGENTS.md`、本文、当前路线和任务相关契约，再核对源码与最近的本地交接。确认本轮目标、修改范围、通过条件以及已有修改的归属。已有未提交文件、未跟踪文件和证据原地保留。

调查、实现、构建与验证在任务范围内直接进行；提交、推送、标签和发布需用户明确授权。需要多代理时，由用户或适用指令安排，主代理负责整合和最终验证，各代理使用明确的任务与文件范围。候选冻结和完整构建由一个主代理串行执行。

## 2. 开发与验证

### 实现

从现有实现、契约和回归入口确定改动点。编辑模型中的 UTF-8 源字节、投影文本、视觉行与几何坐标各有明确含义；缓存键覆盖文档身份、正文、装饰、字体、宽度及影响布局的版本。输入改动核对中文/emoji、反向与跨视口选区、IME、撤销、切页和外部回写。

代码、必要回归和受影响文档同轮更新。新增关键回归时核对 `scripts/check-neoeditor.ps1` 的正式集合；CMake 自动发现与正式检查名单分别维护。

### 选择验证范围

| 改动 | 本轮检查 |
| --- | --- |
| 文档、维护脚本 | 文档检查、受影响脚本的定向回归、`diff --check` |
| 小功能或修复 | 相关测试、增量构建、版本核对、真实窗口预览 |
| 一个功能闭环或一批修复 | 主动向用户提出出可用版本，按当前候选执行完整检查、独立包与实窗验收 |
| 性能优化 | 先测当前基线，再做同规模、同配置、同轨迹 A/B |

完整检查使用当前仓库内的唯一新目录，具体命令见[构建参数与脚本](NeoEditor-发布构建说明-2026-10-02.md)。记录实际测试集合和退出码。失败时按工具预检、配置、编译、断言、包检查或 GUI 定位，保留对应日志。

正确性、性能、真实窗口和独立包分别记录。GUI 按当前 computer-use 技能操作，绑定 EXE、独立 APPDATA、所属窗口、保存/撤销结果与正常退出。未执行的设备、IME、多屏 DPI 或持续拖选只需在该轮验收中简记。

### 性能口径

先确认主要成本，一次处理一个有证据的目标。记录预热、原始轮次、统计口径、配置、窗口/DPI、适配器、源码身份和 EXE SHA256。组件计时、进程 CPU、输入到屏幕延迟分别测量；`EndDraw` 仅表示绘制提交阶段完成。嵌套阶段时间和工作集、私有工作集、私有提交分别列出。复跑方法见[性能测试方法](性能测试方法.md)。

## 3. 文档随改动维护

### 每类信息只维护一处

| 位置 | 维护内容 |
| --- | --- |
| `AGENTS.md` | 新会话的简短入口和执行要求 |
| 本文 | 开发、验证、产物、文档与交接规则 |
| `docs/发版流程.md` | 版本文案、候选冻结、最终资产验收与发布顺序 |
| `docs/当前实现与验收路线.md` | 当前能力、源码入口与待办 |
| 其余 `docs/` | 对应模块的稳定契约与复跑方法 |
| `docs/文档同步记录.json` | 本轮源码内容摘要与逐文档核对结论，随源码提交 |
| 中英文 README、应用 README、发布说明 | 使用者能观察到的功能、操作和版本变化 |
| `local-docs/` | 轮次记录、历史计划、交接与测量报告；由 `.git/info/exclude` 排除 |
| `out/` | 原始日志、数据、截图、配置与哈希 |

其它文档用链接引用规则，避免重复维护步骤和数字。带日期的技术契约文件名保持兼容，正文随实现更新。测试数、版本和产物路径从当前脚本、版本源和命令输出取得；轮次数字写在对应记录中。

### 一轮改动的文档步骤

1. 开始时查看[同步表](目录说明.md#改动时同步哪些文档)，找到本轮涉及的说明和契约。
2. 实现过程中同步行为、入口、数据格式和命令。先中文后英文，核对会随包交付的 `apps/neo_editor/README.md`。
3. 运行 `python scripts/check-docs.py --write-review` 生成 `docs/文档同步记录.json`。逐项核对其中的文档，填写更新内容，或无需更新的具体原因。草稿含空白结论时退出码为 1，填完再检查。
4. 再运行 `python scripts/check-docs.py`，通过后生成交接。代码再次变化会使核对记录失效；重新生成草稿时，对应文档结论会清空，须重新核对。纯内部调整可记录无需改文档的原因。
5. 新增、合并或更名文档时，更新 `docs/文档清单.json` 并用 `--write-index` 生成导航；新增源码模块同时补充 `sync_rules` 映射。
6. 将本轮目标、改动、验证结果和下一步写入本地交接；同步记录与对应源码一同提交。

例如，记录中的 `documents` 可填写：`"docs/查找替换与选区范围.md": "已更新选区失效后的提示与恢复步骤"`，或 `"README.md": "已核对，仅整理内部调用，功能入口和操作不变"`。源码摘要由脚本生成，维护者填写具体结论。

文档先写“如何使用、实际行为、适用条件”。确实未实测或证据不足的内容在相关位置简短注明；详细环境、哈希和覆盖矩阵放轮次记录。旧验收保持原构建与原日期。

### 合并与归档

先把仍有效的内容并入对应契约，更新所有入口和链接，再保留原文到 `local-docs/repo-docs/` 的唯一归档目录；记录原路径、承接文档及原文 SHA256。公开文档需要的规则保留在仓库中，本地材料仅作复查入口。原始报告保留原字节，勘误另写记录。只剩导航用途的旧入口可以保留短链接，避免中断已有引用。

### 可执行检查

`scripts/check-docs.py` 仅依赖 Python 标准库。默认只读，比较 HEAD 与当前工作区，覆盖已暂存、未暂存和未跟踪源码。`--base <Git引用>` 指定比较基准，`--write-review` 更新待核对记录，`--write-index` 生成导航，`--json` 输出机器可读结果。

| 编号 | 检查内容 |
| --- | --- |
| DOC000 | 检查器执行异常或 Git 比较失败 |
| DOC001 | 文档清单格式、完整性、重复项和同步目标 |
| DOC002 | 生成的导航与清单一致 |
| DOC003 | 维护文档和对外入口的相对链接可解析 |
| DOC004 | 对外入口引用随仓库传递的稳定材料 |
| DOC005 | 对外版本简介包含当前产品版本 |
| DOC006 | 改动源码已绑定内容摘要，所有相关文档有核对结论 |
| DOC007 | 改动源码均有文档映射，包括新模块及重命名前后路径 |

`docs/examples/` 是演示夹具，不作为维护文档登记。指向 `local-docs/`、`out/`、旧 `参考/` 的本地材料单独列出存在性，新检出无需带这些目录。源码摘要将文本的 LF/CRLF 视为相同内容，支持换机检出；核对结论保留在仓库，原始过程留本地。检查器核对覆盖和记录，具体行为仍由维护者阅读确认。

检查器及其夹具回归接入 `check-neoeditor.ps1`；开发预览检查、统一发版预检和交接脚本均检查同步记录。交接通过后把核对结论附入快照；预览和交接脚本支持 `-Python <绝对路径>`。

独立文档 CI 在每次 push / PR 运行，使用完整 Git 历史和 `--ci`：push 比较推送前后全部提交，PR 比较共同基线；新分支与默认分支比较，首次建库按空树比较。手动运行检查最近一次提交。纯文档检查无需编译应用；新增机器规则时同步更新上表和定向回归。

## 4. 构建产物与 out/ 管理

开发期增量编译复用本仓库的固定构建树，如 `build-eui-tests/`。正式门禁和打包使用唯一新目录。以下清理只处理本轮创建并确认归属的构建树，先保留配置、日志、诊断和哈希，再删除含 `CMakeCache.txt` 的构建目录；失败轮次在排查结束后清理。已有输出和证据保持原状。

### 预览轮换

- 使用 `out/preview-1/` 至 `preview-3/`，小改动增量构建后覆写最旧槽位，保留 EXE、assets、本轮截图和简要说明。
- 交付前运行 `scripts/check-neoeditor-preview.ps1 -Exe ./out/preview-N/neo_editor.exe -BuildDirectory ./build-eui-tests`，核对版本源、缓存、生成头、RC 与 PE 版本。使用指定版本时传 `-Version`；旧缓存先显式重新配置。
- 小改动按定向测试和窗口预览验收；达到可用版本节点再跑完整门禁。

### 可用版本与归档

- 统一准备入口生成 `out/stable-candidate/`，保留最终单 EXE、SHA256 和验收材料。
- 已有未确认候选保留；需要替换时先向用户说明。用户确认可发版后就地改名为 `stable-v<版本>-<YYYYMMDD>/`。
- 稳定版归档保留最近 3 个；淘汰前确认哈希与发版记录已留存。发布步骤仍按发版流程和实际授权执行。

## 5. 状态与交接

| 状态 | 含义 |
| --- | --- |
| SOURCE | 仅核对源码或静态结构 |
| PASS / FAIL | 已执行指定动作，满足 / 不满足通过条件 |
| OBSERVED | 已观察到现象，尚不足以判定通过或失败 |
| SKIP | 因工具、设备或本轮范围未执行，附一句原因 |
| NOT_RUN | 尚未执行 |

每轮收尾先完成文档检查和 `git -c core.whitespace=cr-at-eol diff --check`，再用 `scripts/write-handoff-summary.ps1` 生成新快照，补齐：

- 目标、实际改动、更新的文档及通过条件。
- 分支、HEAD、dirty/untracked 归属，必要的源码/EXE SHA256。
- 定向测试、正式门禁、真实窗口和性能的结果与证据路径。
- 本轮构建树的保留或清理情况。
- 剩余事项与一个具体的下一步。
- 提交、推送、标签和发布的授权状态。

快照保存生成时状态，具体结论由本轮记录补全。下一位维护者按快照和当前源码继续工作。
