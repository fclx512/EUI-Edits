## 1. 架构与集成方式

**机制**：本后端不是"另一份主程序"，而是把 `core::window` 的窗口后端自由函数（声明于 `core/window/window_backend.h:10-45`）用纯 Win32 实现了一遍，同时在 `core::window::win32` 命名空间下暴露一组宿主 API（`core/window/win32_host.h:6-42`，`Window = void*` 即 HWND，无 GL 上下文概念）。桌面入口只有一份：`glfw_app_main.cpp` 与 `win32_app_main.cpp` 都退化为两行 `#include "core/app/desktop_app_main.inl"`（`core/app/win32_app_main.cpp:1-2`），由编译期宏在 `.inl` 顶部二选一宿主命名空间。

关键点：

- **宿主命名空间选择**：`core/app/desktop_app_main.inl:13-19` —— `EUI_WINDOW_BACKEND_WIN32` 定义时 `#include "core/window/win32_host.h"` 并 `using namespace core::window::win32`，否则走 `core::window::glfwHost`（`core/window/glfw_host.h` 适配层）。两个命名空间的函数签名一致，`.inl` 正文逐字共用。
- **构建开关（CMake 侧）**：`CMakeLists.txt:382-386` —— `EUI_WINDOW_BACKEND` 等于 `"win32"` 时：`target_compile_definitions(eui_neo PUBLIC EUI_WINDOW_BACKEND_WIN32=1)`、`target_link_libraries(eui_neo PUBLIC gdi32)`、入口源码换成 `core/app/win32_app_main.cpp`（经全局属性 `EUI_NEO_APP_MAIN_SOURCE` 传给父工程）。user32/imm32/shell32/winmm 等系统库由 `WIN32` 公共块提供（`CMakeLists.txt` 的 Platform capabilities 段，随 `EUI_TRAY_WINAPI=1` 一起链接）。
- **渲染 API 约束**：`createWindow` 只接受 `RenderApi::Native`（`win32_backend.cpp:341`）；`RenderApi::Native` 来自 `EUI_RENDER_BACKEND_D2D`（`core/render/render_backend.cpp:66-73`）。即 Win32 窗口后端配套 Direct2D 渲染后端，与 `NativeWindowInfo` 返回真 HWND 的约定（`win32_backend.cpp:371`，`{window, window, nullptr, nullptr}`）配对。
- **接口面**：`win32_backend.cpp` 覆盖 window_backend.h 的全部抽象（createWindow/destroyWindow :340-370、nativeWindowInfo :371、currentContextKey :372（恒 nullptr）、timeSeconds :373（steady_clock 起点静态）、postEmptyEvent :374、光标 :392-394、剪贴板 :376-389、图标 :395-409、IME 定位/查询/取消 :410-422、拖放消费 :413、输入回调装/卸 :414-415）；`win32` 命名空间额外提供 live-resize 专有 API（`win32_host.h:34-41`）：`requestRefreshAfter/cancelRefresh/setLiveResize/setPaintBackground/notePresented/notePresentationLost/inSizeMove`。
- **回调分发模型**：每个 HWND 一份 `State`（`win32_backend.cpp:17-39`，含全部回调指针、IME 闩、covered 区域、deadline 等），挂在 `states` 全局 map（:40）。窗口类过程 `procedure` 在 `WM_NCCREATE` 时从 `CREATESTRUCTW::lpCreateParams` 取出 State 写入 `GWLP_USERDATA`（:154-158）。`createWindow` 传 `s.get()` 作最后参数、返回后 `states.emplace`（:352-354）。`initialize()`（:425-441）记录 UI 线程 id、PeekMessage 强制建消息队列、注册窗口类。

### 与框架主循环的配合（按需重绘 + 定时唤醒）

- **泵原语**：`pollEvents` = PeekMessage(PM_REMOVE) + TranslateMessage/DispatchMessage 循环（:443）；`waitEventsTimeout(sec)` = `MsgWaitForMultipleObjectsEx(0, nullptr, ms, QS_ALLINPUT, MWMO_INPUTAVAILABLE)` 后 pollEvents（:444，秒→毫秒向上取整）；`waitEvents` 同款无限等（:445）。跨线程唤醒走 `postEmptyEvent`：向 `uiThread` 投递线程消息 `WM_APP+0x317`（:43, :374），`pollEvents` 的 null-HWND PeekMessage 顺带收走。`platform.cpp` 的 `requestFrame/requestUiUpdate`（platform.cpp:752-762）最终都落到 `postEmptyEvent`。
- **空闲决策**（`desktop_app_main.inl:682-697`）：有动画 → `pollEvents` 忙轮询（配合 `waitForNextFrame` 高精度等待，inl:158-167，`frame_pacing.h` 用 `CREATE_WAITABLE_TIMER_HIGH_RESOLUTION` 计时器）；无动画时 `mainWindowRuntime.idleWakeSeconds()`（`core/app/main_window_runtime.h:99-113`，取 `app::nextTimerWakeSeconds()`——`include/eui/detail/dsl_app_impl.h:370` 转发 runtime 定时器——与子窗口 `earliestTimerWakeSeconds` 的较早者）：`<=0` 立即 pollEvents；有限值 `waitEventsTimeout(wakeSeconds)` 睡到定时器到点；+inf 才无限期 `waitEvents()`。即 `nextTimerWakeSeconds` 体系落到 Win32 侧就是 MsgWaitForMultipleObjectsEx 的超时参数。
- **计时精度**：`TimerResolutionGuard` 在整个会话 `timeBeginPeriod(1)/timeEndPeriod(1)`（inl:114-126）。

## 3. 绘制模型：WM_PAINT 补曝光条带

**机制**：核心假设是"渲染后端直接画在屏幕上（D2D HWND target），延迟没画出来的帧里旧像素仍然有效"，所以 WM_PAINT 不需要全量重画，只需要把"从未被本进程内容覆盖过的新曝光区域"填掉，避免露底色。

- **WM_ERASEBKGND 恒 0**（:172）：注释明确"paint 路径真正填它之前不认领背景覆盖"——防止系统先刷一层白底。
- **WM_PAINT 流程**（:173-196）：`BeginPaint`（rcPaint 自动裁剪到 update region）→ 置 `paintPending=true` → 调 `refresh` 回调（回调链最终走 `paintResizeIfDue`/`runFrame` 完成一帧 D2D 绘制+present）→ 之后只处理两条**曝光条带**：以 `coveredWidth/coveredHeight`（上次成功 present 覆盖到的客户区左上角尺寸，取 min 防越界）为分界，右侧竖条 `{coveredW,0,right,bottom}` 与下方横条 `{0,coveredH,coveredW,bottom}`，各与 `paint.rcPaint` 求 `IntersectRect`，相交才 `FillRect`（画刷色 `paintBackground`，默认 `RGB(245,245,245)`，:29；D2D 后端在 `clear()` 时把 clear 颜色回写给它，`core/render/d2d/d2d_backend.cpp:353-359`），并记 `resizeTrace().record("cover",...)`。BeginPaint 的裁剪保证条带填充不会抹掉仍有效的内容像素。
- **BeginPaint/EndPaint 与 swap 的关系**：这里没有传统意义的 swap——D2D 后端 `present()` 就是 `EndDraw`（d2d_backend.cpp:269-290）。WM_PAINT 里的 BeginPaint/EndPaint 只是向系统交割 update region 的合法性：refresh 回调内部完成绘制后，`present()` 末尾调用 `win32::notePresented(hwnd, w, h)`（d2d_backend.cpp:288）回报覆盖尺寸。
- **covered 区与代的维护**（`notePresented`，:494-505）：present 覆盖整个客户区时 `presentedGeneration=sizeGeneration`、`paintPending=false`、`cancelRefresh()`（挂着的延迟刷新定时器作废）；只覆盖一部分（如 resize 中途）则 `requestRefreshAfter(w, 0)` 安排补帧。**设备丢失**：D2D 遇 `D2DERR_RECREATE_TARGET` 时调 `notePresentationLost`（d2d_backend.cpp:141）——covered 清零、paintPending 置位、立即安排刷新（:487-493），下一帧全量重画。
- **invalidate 路径汇总**：置 `paintPending` 的入口有 WM_PAINT（:175）、WM_SIZE（:198）、WM_EXITSIZEMOVE（:209）、`requestRefreshAfter`（:469）、`notePresentationLost`（:489）；应用层的 `requestUiUpdate/requestFullPaint` 不直接打 WM_PAINT，而是经 `postEmptyEvent` 唤醒主循环由下一帧覆盖（`runFrame` 的 frameRequested 判定，main_window_runtime.h:55-60）。
- **曝光与拖拽 deadline 的优先级**：refresh 回调里 `!inSizeMove()` 时清零 `resizeDeadline`（inl:227-231）——WM_PAINT 触发的曝光帧和拖拽结束后的终态帧不被 live-resize 节流挡住。

## 4. DPI：Per-Monitor V2

**机制**：进程级一次性声明 Per-Monitor V2（`win32_backend.cpp:429`，在 `initialize()` 里），此后所有 DPI 相关查询都按窗口当前 DPI 实时取值，没有任何缓存。

处理点清单：

| 处理点 | 位置 | 说明 |
|---|---|---|
| 声明 | win32_backend.cpp:429 | `SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2)` |
| 初始窗口尺寸 | :346-348 | `GetDpiForSystem()` + `AdjustWindowRectExForDpi` |
| WM_DPICHANGED | :219-224 | 先调 `scale` 回调（LOWORD(w)/96, HIWORD(w)/96），再按系统建议 RECT `SetWindowPos(SWP_NOZORDER\|SWP_NOACTIVATE)` |

**注入框架的路径**：`contentScale` → `getDpiScale(window)`（inl:128-133，x/y 均值）→ 三个消费口：① 逻辑尺寸 `logicalWidth/Height = framebufferSize / dpiScale`（inl:362-365）；② `RenderSurface.dpiScale`（inl:556-557、654-658，进 `beginFrame`，main_window_runtime.h:151-157）；③ `app::update(..., dpiScale, pointerScale)` 内部 `effectiveScale = dpiScale * uiScale()`，同时喂给 `TextPrimitive::setLayoutPixelScale` 统一排版/渲染口径（`include/eui/detail/dsl_app_impl.h:319-326`）。`pointerScale`（inl:135-150，framebufferSize/size 比值）在 win32 后端恒为 1.0（:457-458 两者同源），仅 SDL2 X11 下可能不同。

## 5. IME：输入上下文管理

**机制**：组件自己内联绘制 preedit（通过 `queueTextEditing` 把 composition 串喂给 runtime，`core/input/input_state.h:210-216`），原生侧只保留候选窗 UI，并用 `CFS_FORCE_POSITION` 把合成窗钉在光标矩形上。整个 IME 状态机围绕一个目标：**取消合成时，任何已提交/在途的字符都不能漏进文档**。

- **composition 窗口定位**：`setImeCursorRect`（:410-412，runtime 每帧经 `core::platform::setImeCursorRect` 调入）把光标矩形存 `State::ime`；`placeIme`（:111-124）在其上 `ImmSetCompositionWindow(CFS_FORCE_POSITION)` + `ImmSetCandidateWindow(CFS_EXCLUDE)`，带 `placingIme` 重入闩。触发点：WM_IME_STARTCOMPOSITION、WM_IME_COMPOSITION、WM_IME_NOTIFY（:320-333）。
- **合成串读取**：`imeString(hwnd, flag)`（:102-110）`ImmGetCompositionStringW` 宽→UTF-8。WM_IME_COMPOSITION 分派（:324-331）：`GCS_RESULTSTR` → `queueTextInput`（清 composing 态）、`GCS_COMPSTR` → `queueTextEditing`；`l==0` 视为合成被清空。**WM_IME_CHAR 恒吞掉**（:316-319）：结果串只走 GCS_RESULTSTR 一条路，否则 DefWindowProc 会把它再翻一遍 WM_CHAR 造成双写。
- **cancelIme 宿主侧实现**（:125-152，对外入口 `cancelImeComposition` :422，被 runtime 的 `cancelTextComposition` 在焦点切换/指针按下/shutdown 时调用）：① 若根本没有合成（本窗口与 core 层都无），只发一次空的 `queueTextEditing` 收尾；② 置三重闩 `cancellingIme/cancelledIme/discardCancelledChars` 后才调 `ImmNotifyIME(NI_COMPOSITIONSTR, CPS_CANCEL)`——注释指出 IME 可能在此**同步**重入发 composition/result 消息，闩保证它们进不了文档；③ 用 `PeekMessage(PM_REMOVE)` 按范围清掉已在队列里的 `WM_IME_STARTCOMPOSITION..WM_IME_COMPOSITION` 与 `WM_IME_CHAR`（原生 API 没有代次标识，已 post 的旧消息只能靠范围捞；fresh STARTCOMPOSITION 之前 result-only 消息持续被拒）；④ 全程 `WM_CHAR`/`WM_KEYDOWN` 侧用 `discardCancelledChars/cancellingIme` 拒收（:294-303）。
- **查询路径**：`queryImeComposition`（:416-421，返回 `s->composing && !cancelledIme && !focusLost` 与 GCS_COMPSTR 实时值）在 `consumeTextInput`（input_state.h:284-294）里以原生真值覆盖队列里的 composition 状态——两层状态（core 队列 + 原生 HIMC）以此对齐。
- **失活保护**：WM_ACTIVATE（WA_INACTIVE 或被遮挡）、WM_ACTIVATEAPP、WM_KILLFOCUS、WM_IME_SETCONTEXT(w=FALSE) 四处都在默认焦点/上下文转移**之前**调 `cancelIme`（:240-260），防止 IME 在转移过程中把 raw preedit 定稿。合成期间按键全部放给 DefWindowProc（候选键、Alt+F4），不进应用队列（:289-301，注释说明 Runtime 先发 key 再发 text 的顺序约束）。

## 6. Live resize：deadline 限速直绘

**机制**：拖拽期间 OS 高频派发 WM_SIZE，逐 tick 全量渲染不可行。方案分三层：**后端**负责"把刷新请求合并成到点执行的一次性定时器"；**runner**（WindowState）负责"到点时按刷新率 deadline 决定画不画"；**runtime** 的 `ResizeComposeThrottle` 负责"纯尺寸变化的整树 compose 本身限到约 50ms 一次"（`core/app/dsl_window_runtime.h:34-94`，`kWindowSeconds = 0.050f`）。三层各自节流、互不感知。

- **后端定时器**（:466-484）：`requestRefreshAfter(w, sec)` 要求 `liveResize` 开且非最小化；置 `paintPending`；若已有**更早**的 deadline 则不动（早者赢，:471）；否则记 deadline 并 `SetTimer(hwnd, resizeTimer=0x317, clamp(ceil(sec*1000), 10, 1000))` 一次性定时器。`cancelRefresh` KillTimer + deadline 清零（:477-480）。WM_TIMER 分支（:213-218）到点即 `cancelRefresh` + paintPending 时直绘。拖拽结束（WM_EXITSIZEMOVE）立即 `cancelRefresh` + 直绘终态帧（:208-212）。
- **runner 侧 paintResizeIfDue**（inl:62-104）：`paintingResize` 重入保护；未到期 → 改挂 `requestRefreshAfter(deadline-now)` 等下一次；到期执行 `paintResize()` —— 回调体里跑 `mainWindowRuntime.runFrame(..., waitForDeadline=false)` 完成一帧（inl:540-569，`waitForDeadline=false` 是关键：回调上下文里绝不能自旋睡眠）。执行后 `interval = 1/clamp(refreshRate, 30, 500)`，`resizeDeadline = paintStarted + max(interval, lastResizeCost)`——即"显示器刷新周期与上一帧实际耗时的较大者"作为下一个 deadline，帧率自然退让到绘制能力。
- **notePresented 与定时器的握手**（:494-505）：整客户区 present 成功 → `paintPending=false` + `cancelRefresh`（这帧已画完，定时器无意义）；部分覆盖 → 再挂 `requestRefreshAfter(0)`。
- **FrameGuard**：`MainWindowRuntime::FrameGuard`（main_window_runtime.h:47-50, 181-212）——帧进行中嵌套进来的 runFrame（例如子窗口绘制期间又来 WM_SIZE 回调）直接跳过，只置 `repaintAfterFrame_`，帧收尾时转成 `paintRequested`。注释强调 reentry guard 必须先于任何上下文切换执行（inl:552-554）。配合 `updateManagedWindow` 的 `frameReady()/framePresented()` 失败重试（inl:380-395，失败保持 paintRequested + `requestFullPaint` + `requestUiUpdate`）。
- **逃生阀 `NEO_LIVE_RESIZE=0`**：inl:574-585 用 `GetEnvironmentVariableW(buffer=2)` 读值（恰好 1 字符返回 1，多字符返回所需长度 ≥3——借此区分 "0" 与 "01"），判定逻辑抽成纯函数 `app::liveResizeDisabled`（`core/app/live_resize_option.h:14-16`，精确 "0" 才禁用）。禁用效果：清空 `paintResize`（回调链断）+ `setLiveResize(window, false)`（后端连定时器一起关，:481-484）。
- **与 GLFW 30Hz 的对应关系**：同一函数 `paintResizeIfDue` 里 `#else` 分支保留 GLFW 安全限——距上次绘制不足 `1.0/30s` 直接 return（inl:75-79），且 GLFW 的 refresh 回调仍无条件 `requestFullPaint`（inl:233-235）；win32 路径则不用固定 30Hz，而是 deadline 自适应，refresh 回调不强制全量 paint（暴露帧靠 WM_PAINT 条带机制补）。Win32 路径的注释口径：*"Native DC frames coalesce at the display budget without sleeping inside window callbacks"*（inl:51-53）。

## 8. 已知坑与后续优化方向

### 代码注释里明说的未决问题

1. **IME 取消无代次标识**（:144-146）：原生 API 无法标记"哪些 IME 消息属于被取消的会话"，只能按消息范围 PeekMessage 捞；取消后到新的 STARTCOMPOSITION 之前，result-only 消息会被持续拒绝——若某 IME 在取消后才补发 result，用户输入会丢失。这是已知权衡，换 IME 引擎时需回归测试。
2. **ImmNotifyIME 同步重入**（:139-141）：CPS_CANCEL 可能同步触发 composition/result 消息，靠 `cancellingIme` 闩挡住；闩的生命周期（RAII guard）必须覆盖整个取消序列。
3. **键盘分发顺序假设**（:290-293）：Runtime 先派发 key 再派发 text，所以合成中（即使 preedit 串还空）就必须把候选键挡在应用队列外——这依赖 runtime 的实现顺序，改 runtime 派发顺序时需回看这里。
4. **单文档拖放**（:164）：多文件拖放只收第一个，未做"明确拒绝"的用户提示。
5. **析构顺序防线**（:362-366）：`destroyWindow` 先清全部回调再 `DestroyWindow`，防止拆除期消息调到已退役的 runner/重建输入队列——新增窗口生命周期代码时不可绕过这个顺序。
6. **WM_ERASEBKGND 与背景认领**（:171-172）：注释点明"paint 路径真正填它之前不认领背景覆盖"——背景色的一致性依赖 D2D `clear()` 回写 `setPaintBackground`（d2d_backend.cpp:353-359），若 clear 色与首帧实际内容差异大，曝光条带会闪一下底色。

### 阅读中发现的脆弱点

7. **WM_PAINT 条带模型的前提**：旧像素仍有效。它依赖"D2D HWND target 的绘制与 present 在同一 UI 线程、且 deferred 帧期间没有其他东西重画窗口"。任何全窗口 `InvalidateRect(nullptr)` 的旁路调用都会破坏 covered 记账；`notePresentationLost` 是唯一的自愈口。
8. **requestRefreshAfter 的"早者赢"语义**（:470-472）：已有 deadline 更早时新请求被忽略——若上层先挂了一个长 delay 再想提前刷，必须显式 `cancelRefresh`。当前 runner 侧恰好总是先算更早的 deadline，属于隐式契约。
9. **SetTimer 10ms 下限**（:474）：deadline 不足 10ms 会被夹到 10ms。240Hz 及以上的高刷屏（interval≈4.2ms）实际调度精度被定时器钉在 ~10ms，拖拽期帧率封顶约 100Hz。若要真发挥高刷，需换 waitable timer / 立即直绘策略。
10. **消息处理的 UI 线程单线程假设**：`states`、`uiThread`、`mainHandle` 均无锁；任何后台线程触碰窗口 API 都必须收敛到 `postEmptyEvent` 唤醒主线程。
11. **`wakeMessage = WM_APP+0x317` 与 `resizeTimer = 0x317`**：自选值，与三方库共存时要防 WM_APP 段冲突。
12. **WM_CHAR 孤立高代理**（:306-310）：高代理后跟 BMP 字符时，旧缓存被静默清掉（:309），输入即丢失——理论上 IME 不应产生这种序列，但非 W 通道（如某些输入法经由 WM_CHAR 的路径）值得留意。
13. **WM_SIZE 尺寸为 0**：最小化/极端拖拽时 LOWORD/HIWORD 可为 0，后端照常回调；防护在 runner（inl:214 的 `w>0&&h>0`）与主循环（inl:354、636 的 framebufferSize<=0 分支），后端自身不设防。
14. **`refreshRate()` 失败回退 60**（:465）：`dmDisplayFrequency<=1`（部分驱动对动态刷新率报 1）时退 60；对高刷用户意味着 deadline 偏保守（宁可慢，不会超帧）。

### 取证基础设施（排查卡死/丢帧时先用起来）

- `NEO_GPU_STATS=1`：会话级计数 + 周期心跳落盘（`NEO_GPU_STATS_FILE`，缺省 `neo_gpu_stats.log`；间隔 `NEO_GPU_STATS_INTERVAL_MS`，缺省 1000ms），心跳点 `fb-cb/refresh-cb/paint-enter/paint-done/main-frame`（inl:88-96, 210-225, 652；`core/render/gpu_resize_stats.h:159-200`）。硬挂死时文件最后一行即卡住前的阶段，`lastPaint/maxPaint` 可区分"某次重绘自身耗时爆炸"。
- `NEO_RESIZE_TRACE=1`：进程退出时向 stderr 吐 JSON 事件流（上限 16384 条），事件含 `size/drag-enter/drag-exit/cover/present/bind/end-draw/update/draw`（`core/render/resize_trace.h:20-58`；后端 :190, 201, 206, 211 记录 size/cover/drag）。
- 退出时 `printSummary("desktop_app_main")`（inl:713）。

### 建议的后续优化方向

- **高刷调度**：把 `requestRefreshAfter` 的 SetTimer 换成可等待定时器或"deadline 已过则当场直绘"，消除 10ms 下限。
- **IME 取消代次化**：在 core 层维护一个自增 composition generation（现在 input_state 已有 `compositionChanged` 雏形），代替范围 PeekMessage 的粗粒度清理，减少极端 IME 下的丢字。
- **多文件拖放**：`droppedPaths` 结构已就绪，去掉单文件截断只需放开 :165 的循环上限；属于复用到非单文档项目的第一处改动点。
- **动态刷新率**：`refreshRate()` 可监听 `WM_DISPLAYCHANGE`/`WM_DPICHANGED` 缓存失效，避免 EnumDisplaySettings 每帧调用（当前调用频率由 `updateFrameInterval` 的 0.5s 节流保护，app_runner.h:118）。
- **复用清单**：新项目带走本后端需一并拿走：`win32_backend.cpp`、`win32_host.h`、`desktop_app_main.inl`、`win32_app_main.cpp`、`live_resize_option.h`、CMakeLists 三处开关（win32 分支 :382-386、WIN32 公共库块、`EUI_APP_MAIN_SOURCE` 全局属性），以及配套的 D2D 渲染后端（`core/render/d2d/`）——WM_PAINT 条带与 `setPaintBackground` 依赖它。

## 1. 架构与集成

**机制说明**
D2D 后端是 `RenderBackend` 的一个 Windows-only 实现类 `D2DRenderBackend`（`core/render/d2d/d2d_backend.h:9`，pimpl 结构 `d2d_backend.h:40`）。它不做文本排版，只消费与 OpenGL 后端完全相同的 UI 命令流与共享字形图集——这条边界声明写死在头文件注释里（`d2d_backend.h:7-8`）。**一个重要的架构事实：当前实现没有显式的 D3D11 device / IDXGIFactory / ID2D1DeviceContext / DXGI swapchain**，走的是 D2D1 经典（legacy）RenderTarget 路径：

- `D2D1CreateFactory(D2D1_FACTORY_TYPE_SINGLE_THREADED)` 创建工厂（`d2d_backend.cpp:249`）；
- 窗口目标是 `ID2D1HwndRenderTarget`（硬件/混合光栅，由 D2D 内部自管 D3D 设备）或 `ID2D1DCRenderTarget`（纯 CPU 光栅 + GDI 呈现），二者按 `software` / `gdiPresentation` 标志二选一（`d2d_backend.cpp:108-128`，Impl 字段 `d2d_backend.cpp:75-79`）；
- 像素格式固定 `DXGI_FORMAT_B8G8R8A8_UNORM + D2D1_ALPHA_MODE_IGNORE`、DPI 96、identity 变换直接用设备像素坐标（`d2d_backend.cpp:110-112`、`d2d_backend.cpp:273`）。
- 后端不覆写 `gpuDeviceInfo` / ShaderToy / GpuImage / DynamicTexture 等接口，全部落到基类默认"不支持"实现（`core/render/render_backend.h:185-190,240-278,300-308`）。

对象生命周期：`Impl` 析构时统一 `releaseDevice()`，并 delete 遗留的 Texture 裸指针（`d2d_backend.cpp:95`）；`releaseDevice()`（`d2d_backend.cpp:97-107`）负责弹出未配对的轴对齐裁剪、释放 brush/layer/cache/窗口目标/DC、清空图集与阴影掩码缓存、重置容量状态——它是"设备级失效"的唯一入口，目标重建（`createWindowTarget` 失败或 `D2DERR_RECREATE_TARGET`）都会走到这里。位图纹理本身在设备失效时只 `Reset()` COM 引用，`Texture::bgra` CPU 副本保留作为恢复源（`d2d_backend.cpp:60-65` 注释："Recovery source, never a second RGBA copy"）。

**启用路径（构建宏 + 运行时）**
- CMake 选项 `EUI_RENDER_BACKEND` 取值 `auto|opengl|vulkan|d2d`（`CMakeLists.txt:57-63`）；`d2d` 仅限 Windows 且禁止 SDL2 窗口后端（`CMakeLists.txt:65-67`）；反过来 **win32 窗口后端强制要求 d2d**（`CMakeLists.txt:69-70`），即 win32 与 d2d 是一套绑定实验。d2d 与 GLFW-on-Windows 也可以组合。
- 解析后注入宏 `EUI_RENDER_BACKEND_D2D=1` 并链接 `d2d1`（`CMakeLists.txt:365-367`）。
- 编译期分派在 `createRenderBackend`（`core/render/render_backend.cpp:81-83`）与 `windowRenderApi()`（返回 `RenderApi::Native`，`render_backend.cpp:69-70`）；win32 后端只接受 `RenderApi::Native` 的建窗请求（`core/window/win32_backend.cpp:341`）。
- 运行时开关（环境变量，均在构造函数读取，`d2d_backend.cpp:232-245`）：
  - `NEO_D2D_SOFTWARE=0` → 强制 HwndRenderTarget 硬件路径；**win32 窗口后端下未设置时默认就是 software**（注释："Native low-memory experiment defaults to software even when started directly"，`d2d_backend.cpp:236-238`）；
  - `NEO_WIN32_DC=0`（仅 software 下有效）→ 放弃 DC/GDI 呈现退回 HwndRenderTarget 软件位图翻转（`d2d_backend.cpp:239-241`）。

## 2. 呈现模型：frameReady / framePresented 两段式

**机制说明**
D2D 的帧建立（`BeginDraw` 前）和呈现（`EndDraw`）都可能失败，而 GL 后端不会。为此框架在 `RenderBackend` 新增了两个可失败性虚接口（默认 `true`，即"永不失败"，`core/render/render_backend.h:197-200`），契约注释明确：**失败的帧必须让宿主的 paint 请求保持挂起，包括 cache 错误**。

宿主侧每个 ManagedWindow 的单帧流程（`core/app/desktop_app_main.inl:372-396`）：
1. `beginFrame(surface)`：惰性建目标（`!window` 时 `createWindowTarget`，`d2d_backend.cpp:259`）；比对目标像素尺寸与请求尺寸，不一致时硬件路径 `hwndTarget->Resize`、DC 路径重新 `BindDC`（`d2d_backend.cpp:260-269`，埋 `resizeTrace "bind"`）；然后 `BeginDraw` 并置 `frame=true`（`d2d_backend.cpp:272-274`）。幂等保护：`p.frame` 已置位或尺寸 ≤0 直接返回（`d2d_backend.cpp:257`）。
2. `frameReady()` == `frame && !failed`（`d2d_backend.cpp:253`）。为 false 时宿主**不渲染**：置 `paintRequested`、`requestFullPaint()`、`requestUiUpdate()` 后返回（`desktop_app_main.inl:380-385`）——下一轮循环重试整帧，不会出现半帧上屏。
3. `present()`：先收尾 cache 帧（`endRenderCacheFrame`，`d2d_backend.cpp:278`）、弹出裁剪，再 `EndDraw`（埋 `"end-draw"` trace，`d2d_backend.cpp:281-283`）。`EndDraw` 成功才置 `presented=true`，随后 `win32::notePresented(hwnd, w, h)` 通知宿主"哪些客户区已有有效像素"（`d2d_backend.cpp:287-289`）、记 `resizeTrace "present"`、累加 `RenderFrameStats::backendPresents/backendPresentPixels`（`d2d_backend.cpp:290-292`）。
4. `framePresented()` 为 false 时宿主同样保持 paint 挂起并请求下一帧（`desktop_app_main.inl:388-395`）；只有确认上屏才清 `paintRequested`（`desktop_app_main.inl:389-390`）。

**Present 时机与 sync interval**
没有 swapchain 就没有 `Present(syncInterval)` 可调：HwndRenderTarget 的 `EndDraw` 隐式把位图翻转/混合到窗口（经过 DWM），DC 路径则由 GDI Blit 上屏（`d2d_backend.cpp:114-116` 注释 "CPU rasterization to a native DC; EndDraw presents through GDI"）。帧节奏由 win32 宿主控制：live resize 期间 `paintResizeIfDue` 按 `max(1/刷新率, 上次重绘耗时)` 的 deadline 用 `WM_TIMER` 排队下一帧，不做回调内 sleep（`desktop_app_main.inl:62-104`；GLFW/GL 老路径保留 30Hz 限速，win32+D2D 不需要，注释在 `desktop_app_main.inl:51-53`）。

**按需重绘下避免空转**
- `notePresented`（`core/window/win32_backend.cpp:494-505`）：记录 `coveredWidth/coveredHeight`（已上屏覆盖区）；若覆盖 == 整个客户区，则 `paintPending=false` 并 `cancelRefresh`（杀掉 resize 定时器）——UI 静止时不再产生任何帧。
- `notePresentationLost`（`win32_backend.cpp:487-493`）：设备失效时清零覆盖记录、置 `paintPending` 并 0 延迟请求刷新，保证重建目标后一定有一帧恢复内容。
- `WM_PAINT` 里只对"新暴露的条带"用 `paintBackground` 色补底，BeginPaint 的裁剪自动限制填充范围（`win32_backend.cpp:173-195`；背景色来自 `clear()` 里 `setPaintBackground` 的回写，`d2d_backend.cpp:351-357`）。
- 重绘节流：resize 期间一个 deadline 周期只执行一次真重绘，防重入与限速跳过不计入 `liveResizePaints` 统计（`desktop_app_main.inl:62-104`、`gpu_resize_stats.h:9-11` 口径注释）。

## 3. 几何与图元

**机制说明**
后端层面的图元集合比"render_types.h"更靠上一层：`render_types.h` 只定义基础值类型（Color/Rect/Gradient/Border/Shadow/Transform，`core/render/render_types.h:29-144`），真正的绘制命令结构在 `core/render/primitive_geometry.h`——`RoundedRectDrawCommand`（填充+渐变+边框+阴影+backdropBlur 参数，`primitive_geometry.h:17-32`）与 `PolygonDrawCommand`（`primitive_geometry.h:39-44`），文本命令 `TextDrawCommand` 在 `core/render/render_backend.h:40-46`。每个命令携带 6 个 `PrimitiveGeometryVertex`（screen xyz + local xy，`primitive_geometry.h:12-15`）。

核心技巧是**从顶点对恢复仿射变换**：`transform()`（`d2d_backend.cpp:42-52`）用顶点 0/1/5 的 screen 与 local 坐标解出 2×3 矩阵，使矩形/渐变/路径的几何坐标保持"局部空间"，滚动与缩放只体现为 SetTransform——注释在 `d2d_backend.cpp:40-41`。副作用：**透视/3D 变换无法表达**，会静默退化为仿射（见第 8 节）。

各图元映射：
- **圆角矩形** `drawRoundedRect`（`d2d_backend.cpp:371-394`）：`shadowPass` 分支只画阴影掩码后立即返回（:374）；正常分支按 `gradient.enabled` 走 `CreateGradientStopCollection + CreateLinearGradientBrush`（仅 2 个 stop、`D2D1_GAMMA_1_0`、每帧重建画刷，:377-385）或复用共享 `ID2D1SolidColorBrush`（`solid()` 只改色，:149-151）；边框用内缩 `border*0.5` 的第二个 `DrawRoundedRectangle`（:387-392）。圆角/边框宽度经 `clampedPrimitiveRadius/BorderWidth` 钳制（`primitive_geometry.h:124-130`）。
- **阴影** `shadow()`（`d2d_backend.cpp:188-229`）：不用 D2D 效果，而是 CPU 逐像素生成圆角距离场的 **A8 不透明度掩码**（SDF + smoothstep，:209-218），`FillOpacityMask` 上屏（经 `mask()`，:181-187）。掩码按 8 元组 key（宽/高/圆角/模糊/偏移/spread/inset）缓存，见第 5 节。inset 阴影在同一 SDF 上叠加方向渐变因子（:213-217）。
- **多边形** `drawPolygon`（`d2d_backend.cpp:395-404`）：每帧新建 `ID2D1PathGeometry` + GeometrySink 填边、`FillGeometry`。圆角多边形的圆角化在上层完成（每角 5 段插值，`primitive_geometry.h:196-233`）。
- **图片** `drawTexture`（`d2d_backend.cpp:456-506`）：从 7-float/顶点（screen xyz, local xy, uv）布局恢复仿射（:481-487，保留 fit/crop 语义）；圆角裁剪用 `CreateRoundedRectangleGeometry + PushLayer`，layer 复用单个 `ID2D1Layer`（:492-504）；tint 不是 shader 而是改写 CPU 副本后重传位图（第 5 节）。`blur>0` 只警告一次"image blur pending"（:488-490）。
- **纯矩形**：没有独立命令，radius=0 的 `FillRoundedRectangle` 即矩形；scissor 用 `PushAxisAlignedClip`（ALIASED，`d2d_backend.cpp:360-364`，配对 Pop 由 `unclip()` 保证，:96）。
- **backdrop blur**：`prepareBackdropBlur` 仅警告一次不支持（`d2d_backend.cpp:365-370`）；`roundedRectHasVisibleContent` 上层已把纯 backdrop 剔除（`primitive_geometry.h:52-64`）。

**抗锯齿与文本渲染参数**
当前实现**不使用 DirectWrite，也没有任何 `D2D1_RENDER_PARAM`（ClearType 对比度/gamma）配置**——D2D1 经典 RenderTarget 本就不支持 DWrite 文本管线。文本是"图集位图"路线：灰色字形为 A8 掩码（灰度 AA，源自 FreeType `FT_RENDER_MODE_NORMAL` + `FT_LOAD_TARGET_LIGHT`），彩色字形（emoji）为预乘 BGRA 位图。`FillOpacityMask` 前临时切 `D2D1_ANTIALIAS_MODE_ALIASED` 避免掩码边缘二次模糊（`d2d_backend.cpp:183-186`）；scissor 同样 ALIASED（:363）；其余图元用默认 per-primitive AA。若新项目想要 ClearType，需要迁移到 `ID2D1DeviceContext + ID2D1DeviceContext::SetTextRenderingParams`，属于第 8 节的架构升级项。

## 4. 字形与文本

**机制说明**
字体光栅化**完全走 FreeType，不经过 DWrite**：共享 `FT_Library`（`core/render/text.cpp:624-629`），加载标志 `FT_LOAD_DEFAULT | FT_LOAD_COLOR | FT_LOAD_NO_SVG | FT_LOAD_TARGET_LIGHT`（`text.cpp:51`），彩色位图（emoji, `FT_PIXEL_MODE_BGRA`）与灰度位图（`FT_PIXEL_MODE_GRAY`）分别进入共享图集的 color/gray 两页（`text.cpp:2555-2619`）。图集页规格：gray 初始 512、最大 2048（可经 `NEO_GRAY_ATLAS_INITIAL_SIZE` 调整）、按倍增策略长大（`text.cpp:48-50,711-748`）；color 固定 1024×1024×4（`text.cpp:50,2588`）。页每变化一次 `generation` 自增（`text.cpp:637-641,1753`），页溢出整页作废并推进 `atlasResetEpoch`（`text.cpp:644-668`；图元侧 epoch 失效重排逻辑 `text.cpp:2400-2436` 与 `text.h:45-47` 注释）。

D2D 侧的对接函数只有一个 `Impl::atlas()`（`d2d_backend.cpp:152-180`），由每次 `drawText` 调用（:407-409）：
- **缓存判定**：页 bitmap 存在且 `generation/width/height` 三者匹配才复用（:154），任何图集增长/重置都会因 generation 变化触发重传。
- **通道交换**：`text.cpp` 的 `copyBgraBitmapAsRgba` 已把 FreeType 的 BGRA 换成 RGBA（`text.cpp:1776-1796`），D2D 需要 BGRA，故在此**换回** B/R 通道，且注释明确"不得二次预乘 alpha"——FreeType 彩色位图本身已是预乘的（`d2d_backend.cpp:155-168`）。channels==1 直接走 A8 路径，其余拒绝（:168）。
- **上传**：尺寸变化则 `window->CreateBitmap`（gray 页 `DXGI_FORMAT_A8_UNORM`、color 页 `B8G8R8A8_UNORM`，均 `ALPHA_MODE_PREMULTIPLIED`、96 DPI，:171-175）；尺寸不变仅 generation 变则 `CopyFromMemory` 整页覆盖（:176）。注意页增长后首次上传就是全页拷贝（gray 最大 2048² ≈ 4 MB/次）。

**绘制**：`drawText`（`d2d_backend.cpp:405-426`）按 30 float/字形的步长遍历框架顶点（6 顶点×5 float），从顶点 0/1/5+25 反推每字形的仿射（:416-417），UV 缩放到页尺寸得 source rect；灰色字形走 `mask()`（A8 掩码 + 单色 brush，:422），彩色字形直接 `DrawBitmap`（预乘、线性过滤，:421）。灰色页上传失败则整个命令放弃；彩色页缺失只跳过彩色字形（:407-413）。

这与 GL 路径完全对称：GL 后端消费同一 `TextDrawCommand`（`core/render/opengl/opengl_text.cpp:279-303`），命令由 `TextPrimitive::Impl::render` 统一装配（`core/render/text.cpp:2438-2472`）——**文本布局/塑形/图集管理零改动，后端只换"上传+采样"实现**，这正是复用的关键。

## 5. 缓存与资源管理

**cache_capacity.h 防抖容量策略**（`core/render/d2d/cache_capacity.h:8-23`）
render cache（`ID2D1BitmapRenderTarget`，即 GL 版 FBO 纹理缓存的对应物）的容量按两个维度独立防抖：
- `fits`：请求尺寸 ≤ 容量 → 复用不重建（:10）。
- `oversized`：容量 > 2×请求面积 → 判定"过大"（:11-14），**但必须稳定 2 秒**（`ensureRenderCache` 里 `now - cacheSizeChangedAt >= 2.0`，`d2d_backend.cpp:297-300`）才真正缩容——防止 resize 拖动时反复缩放分配。
- `dimension`：增长时先按"需要 > 之前 ? 之前×1.25 : 之前"做 25% 增长余量，再向上对齐 64 像素，钳到上限（`GetMaximumBitmapSize()`，:15-19；调用点 `d2d_backend.cpp:303-305`）。上限由 D2D 运行时给出（硬件通常 16384）。
- 逻辑尺寸变化只置 `recreated`（通知上层"需要整帧重绘"）而**不触发分配**——专门注释："Logical-size invalidation requests a full repaint, but is not an allocation"（`d2d_backend.cpp:299-302`）。`renderCacheWasRecreated()` 因此有两种来源：尺寸变化或 `cacheInvalid`（:302,321）。
- cache 分配失败时的降级：若窗口目标还活着，清除 `failed` 标志直接走整帧直绘（"A surviving window target can still render a complete direct frame"，`d2d_backend.cpp:313-317`）。
- 分配/释放计入 `gpuResizeStats().addRenderCacheAllocation/Release`（:318-320,328），与 GL 口径一致（容量内复用不计）。

上层调用方是 `core/runtime/runtime_lifecycle.h:202-271`：cache 不可用→整帧直绘；`renderCacheWasRecreated()`→强制 fullPaint；静止帧只 `blitRenderCache(Existing)`；增量帧按 dirty rect 逐个 scissor 重绘进 cache 再 blit。

**blit 的现状**：`blitRenderCache` 忽略 `mode` 与 `dirtyRects`，永远整面 `DrawBitmap`（NEAREST_NEIGHBOR，尺寸相同时无损；`d2d_backend.cpp:342-350`）；`beginRenderCacheFrame` 也忽略 `repaintRects`（:332-336）。部分更新依赖调用方逐 dirty rect 设置 scissor（`runtime_lifecycle.h:255-263`），掩码内仍然全量光栅化——这是与 GL 版 `glBlitFramebuffer` 脏区拷贝的差距，列入第 8 节。

**位图/画刷/几何缓存**
- 字形图集两页：按 generation 缓存（第 4 节）。
- 用户纹理：`Texture` 保留 BGRA CPU 副本（唯一副本，兼作恢复源与 tint 源），GPU 位图尺寸变化才重建、否则 `CopyFromMemory`（`d2d_backend.cpp:432-451`）。
- tint 策略：CPU 改写副本重传位图并记忆上次 tint，tint 不变不重传（`d2d_backend.cpp:460-480`）；RGB 变化才重传，纯 alpha 变化直接用 `DrawBitmap` 的 opacity 参数（:460,502）。
- 画刷：唯一共享 `ID2D1SolidColorBrush` 改色复用（:149-151）；渐变画刷**无缓存**、每次绘制重建（:377-385）。
- 几何：多边形路径几何每次新建（:397-401）；图片圆角裁剪几何每次新建但 `ID2D1Layer` 全局复用一个（:492-499）。
- 阴影掩码：8 元组 key 精确匹配的线性查找缓存；预算 **2 MiB 总字节 + 最多 32 条**，超限整体清空重来（"A bounded mask cache; animated dimensions cannot accumulate indefinitely"，`d2d_backend.cpp:200-204`）；单条上限 8192×8192、单条 >2 MiB 直接放弃（:199-203）。

**resize 资源重建**
设备级：`D2DERR_RECREATE_TARGET` 或目标创建失败 → `releaseDevice()` 全部丢弃，下次 `beginFrame` 惰性重建窗口目标（`d2d_backend.cpp:134-148,108`）；纹理因 CPU 副本存活而自愈（`createTexture` 内部即 `updateTexture`，:427-431）。cache 级：`releaseDevice` 清空容量状态；`releaseRenderCache()` 由宿主在窗口销毁/最小化/尺寸为 0 时调用（`desktop_app_main.inl:321,344,355,608-703`），下次 `ensureRenderCache` 重新分配并强制 fullPaint（`runtime_lifecycle.h:215-218`）。

## 6. retained layer 关闭

**机制说明**
retained layer 是 GL 路径的"子树缓存为纹理"优化：稳定若干帧的子树渲染进 `opengl_image` 管理的持久纹理，之后直接贴图。D2D 后端不实现 layer 句柄族（`createLayer/resizeLayer/beginLayerFrame` 全部落基类默认：返回 nullptr/false，`core/render/render_backend.h:215-239`），因此新增了能力查询虚函数 `supportsRetainedLayers()`（默认 `true`，`render_backend.h:212-214`），D2D 覆写返回 `false`（`d2d_backend.h:15`）。基类注释给出了动机："A backend without retained targets must bypass layer warmup as well as allocation, otherwise an unsupported layer keeps requesting idle frames"——不支持却放行会让 runtime 反复预热、反复请求空闲帧。

三处判定点（均在 `core/runtime/runtime_render.h`，都是加在原有条件前的短路判断）：
1. `renderRetainedSiblingRun` 入口：`runtime_render.h:539`（兄弟节点连续 run 合并缓存）；
2. `renderRetainedLayer` 入口：`runtime_render.h:770`（单元素子树缓存）；
3. `renderRetainedElements` 入口：`runtime_render.h:814`（两个入口共用的实现层，防未来新增调用点绕过）。

三处都同时伴随 `retainedLayerRenderDisabled_`（用户级禁用开关）检查，D2D 下效果等价于"全局关闭 retained layer"，子树恒走直接绘制；`RenderFrameStats::retainedLayerHits/Misses/...` 对 D2D 恒为 0。附带收益：D2D 后端也因此完全不会触发 `gpuResizeStats` 的 retainedLayer 分配/释放计数（该口径注释 `gpu_resize_stats.h:12-14`）。

## 7. 观测设施

**gpu_resize_stats.h（进程级累计计数器 + 心跳落盘）**（`core/render/gpu_resize_stats.h`）
- 设计动机：`RenderFrameStats` 是逐帧 thread_local 且每帧清零（`core/render/render_backend.cpp:22-27,44-50`），不能做进程级累计；GPU 硬挂死（LiveKernelEvent 141）取证需要"卡住前最后一行"（文件头注释 `gpu_resize_stats.h:1-29`）。
- 内容：framebuffer/window refresh 回调数、liveResizePaints（真实执行的重绘数）、renderCache 与 retainedLayer 的分配/释放对、resize 重绘耗时（末次/历史最大，微秒）。
- 开关与落盘：仅 `NEO_GPU_STATS` **精确等于 "1"** 启用；心跳按 `NEO_GPU_STATS_INTERVAL_MS`（缺省 1000，下限 50）追加写 `NEO_GPU_STATS_FILE`（缺省 `neo_gpu_stats.log`），阶段切换允许 100ms 插行，写失败永久放弃不重试（`gpu_resize_stats.h:41-44,86-137,159-200`）；退出时一次性 stderr 汇总（:203-228）。计数全部 relaxed 原子、默认路径零 IO。
- 心跳埋点在宿主重绘路径：`paint-enter`/`paint-done` 包住 `paintResize()`（`desktop_app_main.inl:88-96`）；重绘耗时 `addResizePaintDuration`（:93）。
- **D2D 后端接入的埋点**：cache 分配/释放对——`ensureRenderCache` 替换旧 cache 时先 release 后 allocation（`d2d_backend.cpp:318-320`）、`releaseRenderCache`（:328）、`releaseDevice` 释放 cache（:100）。retainedLayer 计数因第 6 节的门控恒不触发。

**resize_trace.h（有界内存事件流）**（`core/render/resize_trace.h`）
- `NEO_RESIZE_TRACE=1` 启用；环形上限 16384 条、溢出计 dropped（:32-36）；**析构时一次性以 JSON 行输出到 stderr**（`[resize-trace] {"events":[...],"dropped":N}`，:37-47）——正常退出才落盘，不追求崩溃取证（那是 gpu_stats 心跳的职责）。测量帧路径内无同步 IO。
- 提供成对测量助手 `resizeTraceStart/End`（:55-58）。
- **D2D 后端接入的事件**：`"bind"`（Resize/BindDC 耗时，`d2d_backend.cpp:262-268`）、`"end-draw"`（EndDraw 耗时，:281-283）、`"cache-allocate"`（CompatibleRenderTarget 分配，:308-312）、`"present"`（零耗时打点，:290）。宿主侧另有 `"size"`、`"drag-enter/exit"`（`win32_backend.cpp:201,206,211`）与 `"cover"`（WM_PAINT 暴露条带补底，:190）。

**RenderFrameStats**（`core/render/render_backend.h:48-85`）：逐帧 thread_local 统计，D2D 只填 `backendPresents/backendPresentPixels`（`d2d_backend.cpp:291-292`）与经由通用路径的 clear/renderDirectPasses/dirtyRect 等字段；`backendIncrementalPresents` 等字段为 D2D 恒 0（无增量 Present 能力）。

## 8. 实验性现状、已知坑与后续优化

**代码注释明示的限制**
- 后端自述 experimental（`d2d_backend.h:7`）；backdrop blur 未实现，仅警告一次（`d2d_backend.cpp:365-370`）；图片 blur 未实现，警告一次（:488-490）。
- 默认 software + GDI 呈现是"低内存实验"的刻意选择，不是 bug（`d2d_backend.cpp:236-241`）——新项目若要性能，第一件事是 `NEO_D2D_SOFTWARE=0` 走硬件路径。
- 无 DWrite/ClearType、无 ID2D1Effect（阴影靠 CPU SDF、渐变只支持 2 stop 线性），这些是 legacy RenderTarget 的能力天花板。
- retained layer 关闭（第 6 节），稳定子树 UI 每帧全量重绘。

**阅读中发现的脆弱点**
1. **`D2DERR_RECREATE_TARGET` 恢复路径**：`check()` 覆盖了所有绘制/上传调用（`d2d_backend.cpp:134-148`），但恢复依赖 `notePresentationLost + requestUiUpdate + requestFrame + postEmptyEvent` 的组合（:140-145）；在 **GLFW 窗口后端**下 `EUI_WINDOW_BACKEND_WIN32` 未定义，`notePresentationLost` 整段消失，只靠 platform 请求帧——GLFW 的 framebuffer 回调是否会补一帧未被验证。另外 `EndDraw` 失败时**本帧所有已提交绘制全部作废**（D2D 语义），宿主靠 requestFullPaint 重来（`desktop_app_main.inl:388-395`），长时间 D2DERR 会表现为持续重绘风暴。
2. **3D/透视变换静默退化**：`transform()` 只恢复仿射（`d2d_backend.cpp:42-52`），带 perspective/rotateX/Y 的元素会画错位置而不报错；上层 `TransformMatrix` 有 pw 投影（`render_types.h:134-144`），GL 路径支持、D2D 不支持。
3. **多窗口**：每个 ManagedWindow 独立后端实例、独立 factory（单线程工厂，`d2d_backend.cpp:249`），机制上可行；但 `presentedGeneration`（`win32_backend.cpp:31,500`）目前**只写不读**，跨窗口/遮盖恢复的正确性实际依赖 `coveredWidth/Height` + WM_PAINT 补底，语义较脆弱。
4. **混合 DPI**：目标固定 96 DPI + identity 变换，全部按设备像素工作（`d2d_backend.cpp:112,273`），`WM_DPICHANGED` 由窗口层处理并触发重绘（`win32_backend.cpp:219-224`）；跨显示器拖动时图集按设备字号重新栅格化（`text.cpp:1609` 的 ppem 注释），没有发现错误，但 DPI 变化瞬间必然整帧重建（cache `cacheInvalid` + fullPaint），无平滑过渡。
5. **阴影缓存整体清空**：超 2 MiB 或 32 条直接 `shadows.clear()`（`d2d_backend.cpp:204`），动画中尺寸连续变化时会反复清空重建（每条一次 CPU O(w×h) SDF 计算），是潜在的 CPU 尖刺源。
6. **图集整页重传**：gray 页每次增长全量 CopyFromMemory（最大 4 MB，`d2d_backend.cpp:176`），长文本首屏+增长期有明显上传开销。
7. **blit/渐变/路径无脏区与缓存**：`blitRenderCache` 忽略 dirtyRects（`d2d_backend.cpp:342-350`）、渐变画刷每帧重建（:379-385）、多边形几何每帧新建（:397-401）——高频动画下分配压力集中在这些点。
8. **窗口目标像素格式 `ALPHA_MODE_IGNORE`**（`d2d_backend.cpp:112`）：依赖 DC/GDI 呈现时不支持 per-pixel alpha 的分层窗口场景；如需半透明窗口需换 `PREMULTIPLIED` + DComposition 路线。

**后续优化建议（按性价比排序）**
1. **迁移到 ID2D1DeviceContext + DXGI swapchain**：解锁 ClearType（`SetTextRenderingParams`）、`ID2D1Effect`（阴影/blur/DW 首选）、增量 Present（`DXGI_PRESENT_DIRTY_RECTS`，正好填上 `backendIncrementalPresents` 统计）、device-loss 恢复的标准化；同时可把 CPU 阴影 SDF 换成 GPU effect。
2. **硬件路径调优**：默认 software 是过渡态；`NEO_D2D_SOFTWARE=0` 下用 `gpu_resize_stats`/`resize_trace` 对比 cache 分配次数与 end-draw 耗时再定默认值。
3. **脏区 blit**：HwndRenderTarget 下可用 `DrawBitmap` 的 source/dest rect 对 dirty rect 做局部拷贝，接口签名已留好（`blitRenderCache` 的 `mode/dirtyRects` 参数）。
4. **渐变画刷/路径几何缓存**：按 (颜色对,方向,矩形) 或 (顶点签名) 做 LRU，消除每帧 Create 调用。
5. **backdrop blur 补齐**：迁移到 DeviceContext 后用 `CLAMP` + `GAUSSIAN_BLUR` effect 即可对齐 GL 行为（GL 路径的 `backdropCaptures` 统计口径在 `render_backend.h:73-74`）。
6. **`presentedGeneration` 语义落地或删除**，遮盖/恢复路径补一层测试（最小化→还原、Alt+Tab、跨 DPI 拖动三个场景）。
