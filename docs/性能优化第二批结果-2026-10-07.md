# 性能优化第二批结果（2026-10-07）

本批消除输入组件交互回调重复持有长行光标度量的成本。相对于[首批候选](性能优化首批结果-2026-10-07.md)，长行拖选时常驻内存进一步降低，独立阶段 trace 中编辑视图构建时间缩短；总拖选 CPU 的前后区间仍重叠，不据此声称拖选卡顿已解决。

候选为 `out/performance-20261007-r2/EUI-Edits.exe`，包含首批横向离屏片段过滤和本批回调共享布局。SHA256 为 `f893c53197dc72f64cf324adca9c03e03206079b35fdb538e40dc04eb7d5d4d1`。基线是上一批 r1，SHA256 为 `870d2f6d5c352a86983813217151a959e700340f51a6d67868dbd8b733dc93da`。已验收修复仍在本地提交 `44123ad`；两个性能批次保留在工作树，未提交、未推送。

## 改动与结构证据

`InputLayout` 原来按值进入 press、release、context menu、move、drag、cursor 和 scroll 七个回调，内部的 `TextMetrics` 包含完整光标字节/横坐标数组。超长未换行行会被复制到每个闭包，框架复制回调时继续深拷贝这些数组。

`components/input.h` 现在每帧创建一个 `shared_ptr<const InputLayout>`，七个回调共享它。布局对象在 builder 返回后仍存活；原有 `InputState` 的行、表格和几何缓存继续按原生命周期使用，没有更改解析、正文存储、布局缓存失效、滚动或命中算法。不能把它解读为旧回调可跨文档/InputState/preedit 销毁继续调用。

Luna 编写 `input_callback_layout`，主代理审查并运行优化前/后版本，另一位 Luna 只读检查生产补丁与测试边界。测试使用真实 InputBuilder，单条混合 ASCII/中文/emoji 长行有 72000 Unicode codepoints、192000 UTF-8 字节；分配探针只在复制七个回调时启用。

| 复制七个回调 | 分配字节 | 分配次数 | 单次信息性耗时 |
| --- | ---: | ---: | ---: |
| 原实现 | 4034546 | 21 | 1.1076 ms |
| 共享布局 | 480 | 4 | 0.0016 ms |

原实现只在“回调不复制长行数组”断言失败（退出码 1），其命中检查通过；优化后测试退出码 0。耗时不是测试门槛。它还实调七个回调，验证 builder 返回后调用、UTF-8 边界、多行命中、销毁旧回调副本并重建后使用新的横向滚动偏移；模型完整度量继续保留。

## 真实鼠标 A/B

每个样本每版三个新进程，先稳定 2 秒，再以 50 Hz 发送固定物理鼠标轨迹 6 秒，松手后采样 3 秒。J80/J320 在首行 x=120–1000、y=80 往返；JP80 首行只有 `[`，所以使用视口内 y=80–400 的斜向轨迹。最终落点固定并复制校验：长行选区 80 字符、JP80 选区 187 字符，两版每轮选区哈希完全相同且为精确源文子串。这是固定视口补充实验，不替代原计划 10–15 秒跨屏拖选。

条件沿用首批：开发机 Core Ultra 9 275HX/24 逻辑核，系统 DPI 120，Win32/Direct2D Release x64、软件 D2D、窗口 DC；字号 16、UI 缩放 1、行号/可读宽度/动画开，客户端 1262×753。各轮独立 APPDATA/TEMP、`NEO_SINGLE_INSTANCE=0`。CPU=应用进程内核与用户时间增量/墙钟，100%=一个逻辑核；内存为拖选稳定采样期中位数，不是首开峰值。运行期间持续检查前台与 PID/HWND 归属，没有同时编译或运行单测。

| 样本 | 拖选 CPU 中位数（逻辑核） | 专用提交量（MiB） | 工作集（MiB） |
| --- | --- | --- | --- |
| J80，82188 UTF-8 字节、单行 | 0.906 → 0.857 | 54.3 → 46.8 | 56.8 → 48.3 |
| J320，328451 字节、单行 | 0.872 → 0.862 | 81.9 → 68.2 | 98.8 → 70.3 |
| JP80，110270 字节、7561 行 | 0.776 → 0.724 | 62.8 → 62.6 | 70.1 → 69.3 |

两份长行的专用提交量分别减少 7.4/13.6 MiB，三个轮次的内存区间不重叠；格式化对照几乎不变。CPU 各组前后区间重叠，尤其 J320 变化小，因此只确认副本和内存收益，不用中位数下降百分比宣称整体拖选性能通过。松手后低负载有短窗口波动，原始值全部保留。

18 轮有效 A/B 全部正常退出码 0。第一次 JP80 使用同一首行水平轨迹，产生空选区，列为无效轮并单独正常关闭，没有混入汇总。PowerShell/OLE 剪贴板快照的启动尝试没有产生优化版有效轮次，保留启动日志；后续改为 Win32 全局内存格式原样备份/恢复，含 Chromium 注册格式，避免反序列化 opaque 数据，没有输出剪贴板内容。

## 单独的阶段 trace

复用现有 `NEO_TABS_TRACE`，每版单独跑一轮 J80；以同源 Windows QPC 微秒记录拖动区间，筛选区间内的应用 trace。没有新增生产打点，trace 轮不并入 CPU A/B。

| 阶段 | r1 中位数 | r2 中位数 |
| --- | ---: | ---: |
| editor-view | 1.045 ms | 0.271 ms |
| 整个应用 compose | 2.595 ms | 1.747 ms |

区间内分别记录 537/613 次 compose。构建次数不同，说明不能把构建时间下降直接换算为总 CPU 下降，更不能当成帧率或输入响应时延。trace 只覆盖应用构建阶段，没有完整布局/diff/呈现、输入排队和端到端 p95/p99。下一处调查应继续量化输入事件、重复构建与绘制，而不是继续假设长行副本解释全部负载。
