# 性能优化第五批：Win32 消息泵分批返回

本节点完成一项独立的主循环改进：Win32 消息泵在持续消息积压时分批返回，让主循环有机会更新与绘制。**OPT-001 原始高频滚轮停滞的根因仍未确认**，不能把本补丁称为该问题已经解决。

## 调查和实现

滚轮在 [input_state.h](../core/input/input_state.h) 用两个 double 累加值合并，每次 runtime 更新消费一次并清零，没有无限增长的 wheel 容器。[virtualList](../components/virtuallist.h) 只构建可见/overscan 行；惯性速度有既有上限，本批未改滚动手感、增量或上限。

新增 [virtual_list_wheel](../tests/unit/virtual_list_wheel.cpp) 通过真实输入队列、Runtime、宿主 compose/update 与 VirtualList，验证 25000 次入队的增量不丢失、只消费一次、按窗口隔离；随后用 10001 项、22 px 行高、600 px 视口走到实际最大 offset，检查真实最后行、正向单调、边界不重复构建和反向恢复。

| 模拟输入节奏 | 到底帧数 | 最大构建行数 | 中途停滞帧 |
|---|---:|---:|---:|
| 1 tick/frame，dt=1/120 秒 | 3848 | 57 | 0 |
| 25 ticks/frame，dt=1/120 秒 | 3844 | 57 | 0 |
| 25 ticks/frame，dt=0.003 秒 | 10342 | 57 | 0 |

这是无头调度模拟，不是原 Win32 高频注入/呈现的复现。旧 B05 压力脚本还存在“连续截图不变便视为到底”的判据局限；原记录继续保留，不据 `reached_bottom=true` 认定快轮已到达末项。名义 25 tick/3 ms 突发节奏也不能等同整段平均频率。

进一步确认 [Win32 pollEvents](../core/window/win32_backend.cpp) 原来循环直到消息队列为空。新增 [win32_event_pump](../tests/unit/win32_event_pump.cpp) 创建自有、不可见的 message-only HWND，并投递 5000 条普通自定义消息：旧实现一次处理全部消息，新实现按每次最多 **256 条或 2 ms 软时间预算** 返回，剩余消息由下一次 pump 继续处理。仍使用原有无过滤 PeekMessage/TranslateMessage/DispatchMessage 路径；测试验证普通 posted 消息的顺序和完整性，不声称所有 Win32 消息类别具有统一 FIFO。

| 消息泵测试 | 首批消息数 | 全部处理所需 pump | 顺序错误 | 测试结论 |
|---|---:|---:|---:|---|
| 原实现负例 | 5000 | 1 | 0 | 退出 1，分批断言失败 |
| 优化后 | 256 | 20 | 0 | 退出 0，通过 |

时间预算在回调之间检查，单个 WndProc 或模态处理仍可超过 2 ms，不能称为硬响应上限。没有用单次日志耗时计算通用加速比例。既有主循环下一轮继续 pump；空闲等待使用 MWMO_INPUTAVAILABLE，剩余消息会唤醒等待。WM_QUIT 的现有语义没有改动。
